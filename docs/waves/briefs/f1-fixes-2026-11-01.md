## 1. A spent key must not satisfy idempotency (owner-reported, live)

Evidence: `factory spawn list` (token) has 140 `started` spawns, 113 of them with classic-herdr panes (`w4V:p3J`, …), whose
agents are long gone. `rd wave iris` without `(Wave N)` in the prompt derives the key `iris-w1` (`dotfiles/scripts/
remote-dev.sh:745-768`: the counter only sees live hc terminals), `POST /spawns` answered the stored `started` row, nothing
started, and rd printed "wave 1 started … pane w4V:p3J". Any rerun of a wave number collides the same way (`iris-w19b`
was a manual workaround).

- **Derive a spawn's end, don't store it:** a `started` spawn whose session is `dead` (or that never got a session and
  whose pane is no terminal of the current core) reads as a new status `ended` in every view (`Spawn` in
  `packages/contract`, `spawn list|get`, status). This covers the 113 old records without a data migration; if some cannot
  be derived (no session row at all), a one-off additive migration that records the missing `pane_gone` facts is fine.
- **Create on a spent key:** a create whose key belongs to an `ended` spawn answers `409` with a structured error
  (`key_spent`, the stored spawn in the body); the replay of a live or queued key keeps answering 200 with the row, as now.
  Never revive a row silently: a replayed old create must not start work again.
- **rd** (`factory_spawn`, `factory_spawn_report`): on `key_spent` derive the next key (`<key>-r2`, `-r3`, … clipped like
  `wave_agent_name`, then the agent name follows the key) and create again; treat `ended` as not started; the "started"
  line is printed only for a spawn whose session is live. Today a structured error makes rd **fall back to bare hc**
  (`return 2`): `key_spent` must never take that path. So the rd half goes live **before** the server half; say so in the
  report and make the old rd's behaviour against the new server explicit in the commit message.

## 2. A core restart strands a session that was mid-turn

`dotfiles/scripts/hc-resume.ts` (LaunchAgent) types `claude --resume <id>` into every kept terminal with the resume labels
after a core restart; it types no prompt. The resumed session's `session_started` (source `resume`) is a hook event, so
the factory's restart rule skips it (`packages/server/src/rules.ts:208-209`, `HOOK_KINDS` in `sessions.ts:128`) and nobody
says "continue": the session idles mid-work and its orchestrator's wake never fires. If hc-resume is slower than
`RESTART_SETTLE_MS`, the factory starts a second copy of the same conversation in a new tab.

Fix so each session has one resumer: for a factory spawn (`factory.key` label), the factory owns it. Preferred shape (argue
another if the code says so): hc-resume skips terminals carrying `factory.key`; the restart rule then resumes as it does
today. Alternatively keep hc-resume universal and change the rule to type its `continue` note into a session that was
resumed in place (a `session_started` with source `resume` and no `turn_started` since the restart) instead of skipping it,
with a guard that the factory never starts a second copy while hc-resume may still act. Test the chosen path with the hc
fake (`packages/server/test/support/fake-hc.ts`) and, if you touch hc-resume, its own test.
