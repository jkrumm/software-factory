# Brief: F2 Wave 4, evidence, the hold and finalize

You run on the `deep` role (Opus/high): this is what makes an autonomous ship safe, and a wrong transition is silent. Read `AGENTS.md`, `docs/waves/f2.md` (goal and Wave 4), `docs/design.md` §4, §5 ("Done means evidence", "Following a lead"), and `packages/server/src/issues/` and `projects/` (Waves 1 to 3, live) first. The steps are Wave 4 of `f2.md`.

1. **Required evidence** is derived, never declared: from the commits the lead merged (the Issue's `factory/<issue>-<attempt>` branch against its base, by the merged SHAs the lead reports with `ship`, resolved with git with `childEnv()` and a process timeout, outside a transaction) against the manifest's paths (§5's table: UI, API or service, infra or config, data or migration, nothing deployed). `ship` is refused without it (an inbox row answered with what is missing, the CLI exits non-zero and says so); `close` is refused when the commits touch deployable paths. The factory checks existence and freshness (recorded after the merged commit's time), never judges. `factory issue evidence <id> --kind <k> [--link <url>|--file <path>|--stdin]`, payload ≤ 32 KiB, stored in `evidence`.
   No manifest: `close` with the commit or the document is enough.
2. **`watching`:** `ship` moves it to `watching`, sets `wake_at` to now + the manifest's `hold` (default 30 min). The tick turns a passed `wake_at` into a `hold_over` inbox row (key `hold:<issue>:<attempt>`). Handling it runs `make verify` in the repo (the deployed checkout, the make contract says if it exists; process timeout, `childEnv()`, outside a transaction) and the probes (an HTTP GET per probe with a timeout; pass or fail, never averaged). Green → `closed` with the results in `evidence`. Red → back to `working` with a note to the same lead (prompt id `issue:<id>:regression:<n>`), which stays open through the hold; the results are in the note as data. Ports run outside any transaction: claim, commit, call, record. A crash between any two steps replays to one effect.
3. **Finalize once from every exit path** (`closed` by hold, `close`, `drop`, a stop): terminal state, claim released, tab closed, worktree removed (only when clean and its commits are on the base; otherwise kept with a line for the owner), next Issue promoted, the attempt's transcripts copied into the archive (`FACTORY_ARCHIVE_DIR`, default under `~/.local/share/factory/archive/<issue>/<attempt>/`, stored and linked in `issue_links` or `evidence`, never parsed). An `issue_finalized` key makes it once. `factory issue resume <id>` opens the archived session with `--fork-session` through the Runner.
4. **`closed → queued`:** `factory issue reopen <id> --reason <text>` for the same fault within 30 days of closing; past 30 days it is refused with a pointer to `issue new`. It is the only way a closed Issue moves. A new attempt number, a fresh worktree.
5. **Alert leads go on here.** `FACTORY_ALERT_LEADS` (Wave 3 left it off) defaults on once this wave is deployed: decision 3 is "only once F2 Wave 4 is live". Say in the design where the switch went.

Tests: a golden test per path (ship refused, ship accepted, hold green, hold red and back, close refused, close accepted, drop, reopen in and past 30 days); the replay test crashes after every effect of the hold and finalize, zero duplicates; a seeded red `make verify` reaches the lead as exactly one note. `packages/server/src/issues/lifecycle.ts` stays under the §4 reversal bound (about 500 lines): past it, stop and report.

**Gate:** `make check` green, `/review` with findings fixed, one more `/review` pass on the fix commits. **Wait for every review run in the foreground** (`agw run wait <runId>`): never end a turn while a background shell runs, the factory reads your idle prompt as finished and wakes the lead. Push the branch, open a PR (`gh pr create`, no attribution), don't merge or deploy. End with a report: done / deferred, one line each, and the lifecycle module's line count.
