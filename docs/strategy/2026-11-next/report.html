What I recommend

The six gaps

  1. No owner surface. Herdr board, Argo Agents, Iris Decisions, factory status: each answers part of the question, none says what happens next.
  2. No artifact chain. A plan or report lives in a chat turn or a file. Your feedback is a note in prose with no anchor and no record of what you approved.

6. The UX concept

Rules

  • Calm by default. An empty home says "Nothing needs you" and why that is true. Everything else is one step away.
  • Three questions per screen: what needs me, what changed, what happens next. Every wait states what it blocks and what happens if nobody answers.
  • One bright element. The accent colour means "waits on you" and nothing else. Status colours always carry a label.
  • Words, no ids. Titles and summaries come from the digest, which /v1 already provides. An Issue number appears only as a link.
  • Quota sits beside the run count, in the top bar, with the limit marked on each meter.
  • Fails to something useful. A stale snapshot shows its age. A failed read shows an error, never an empty inbox.
  • Peek before attach. A row shows the last reply. Only the terminal holds the transcript.

The chain below is optional per Issue. A bug fix goes straight to Build and Evidence. The two highlighted steps are the only places it can wait on you.

How it works

  1. factory artifact put <issue> report.html --kind concept --ask review stores an immutable revision with its hash. --ask fyi never waits.
  2. With review, the lead ends its turn. The Issue waits and frees its repo claim, exactly as a decision wait does today (settleClaims).
  3. ntfy and Iris link to the page. You select text and comment, or tap a verb. Drafts survive a new revision.
  4. The verdict is saved as an event first. Then a prompt with a deterministic key (artifact:<id>:<rev>:<verdict>) delivers it as the lead's next turn, through the existing prompt path. A replayed tick cannot send it twice.

const Verdict = z.enum(['looks_good', 'with_notes', 'changes', 'stale', 'read'])
  • Storage: blobs under ~/.local/share/factory/artifacts, rows in the factory schema. Never in git, since this repo is public and a work repo's artifact must stay out of it.
  • Safety: agent HTML runs in a sandboxed iframe on its own origin with a strict CSP. Comment text is data for the lead, as an ask's answer is today. Plannotator's sandbox attributes were not verified, so this needs its own design.
  • Visible repos: an IuRoot artifact stays local, with no digest and no agw call, following scopeOf.

The question format

The cards in the decisions section are a working example. A lead writes a spec, zod validates it and names the failing element, and the page renders it. A question with no cost or no consequence is refused before it reaches you.

  1. Title: a noun phrase, the decision and not the run.
  2. One sentence, ending with what happens if nobody answers.
  3. Two or three options, each with its cost. The recommendation sits in the label with its reason, and nothing is pre-selected.
  4. Evidence: one link to the diff or artifact it depends on.
  5. Age, what it blocks, what it does when it expires.

No source measures a 30-second answer, so that target stays untested. We will learn it from answered_at minus opened_at.

The taste gate

A model has no taste, so taste stays yours and the gate spends as little of it as possible.

  • When: a new screen, a new interaction, a new public text. Classify sets taste: true, you can set it, and a note overrides it either way. A wrong classification costs one commit.
  • What the lead does first: writes the five direction lines from the product's own words, renders 2 or 3 variants with real data, and hands them over as a concept with --ask review.
  • What a machine checks first: a slop grep with file and line (transition-all, gradient text, off-grid pixels, emoji, tracked capitals) and the verifier's before and after screenshots. Evidence goes stale when the commit changes.
  • What the judge never does: answer a taste question. It answers everything else first.

8. The improvement loop

You asked for an infinite loop of agents reviewing the factory. I would build a counter instead, because the facts are already in the event log and a counter costs no tokens. Models come in only when something crosses a threshold.

  1. Ledger (SQL, no model). A view over issue_events: refusals by reason, red verifies, steward acts, undeliverable notes, dropped alerts, owner touches. Each row gets a signature.
  2. Threshold (Warp's shape, our numbers). A signature that reaches 10 occurrences, or an oldest occurrence of 7 days, files one Issue of source improve, keyed by signature, with the evidence in its facts.
  3. Fix. A lead makes the smallest change: a brief line, a refusal message, a hook, code. It runs through the normal gates. The apply guard is the review and the hold.
  4. Proof. The signature's weekly count, before and after, on the Issue. If it does not fall, it files again with that fact. This is the pattern track U already uses with finding-changes.json.
  • Was the ask needed? Deterministic: an owner answer equal to the lead's recommendation is a signal that the ask could have been a default. It feeds the judge's input. A taste ask is excluded.
  • Sorting owner notes needs one cheap agw call per week, in a batch, sent only for ordinary repos. It runs near the end of a window with room left, Blume's idea.
  • No evals. Warp's replay benchmarks are "not cheap to run" by its own words. Your rule stands: measure real use.

11. The public project

The repo is public and has no license, so people can read it but have no grant to reuse it. The pitch you describe is a pattern plus a reference implementation, and that is achievable. A product for others is a different job I would not take on.

The pattern, in the words I would use

  • Facts stored, state derived. Hooks write events, "stuck" and "waiting" are computed on read.
  • Interactive sessions in durable terminals, one per Issue, supervised by deterministic code that never calls a model.
  • Capacity is a first-class resource: claims, per-account caps, windows, load.
  • Shipped means verified in production, and the gates are code, since what an agent is told does not change what it can do.
  • The owner decides taste and big bets. Everything else has a steward and a judge in front of it.
