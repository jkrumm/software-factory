## Bottom line

**Effect 4 is genuinely stable; the parts you would want for durable orchestration are not.** `effect@4.0.0` shipped 30 September 2026 and `4.1.0` on 29 October 2026, with a published LTS promise (bug fixes until September 2029 or one year after 5.0, security fixes until September 2029 or two years after 5.0) and lockstep versions across the whole ecosystem. But `cluster`, `workflow`, `sql`, `http`, `rpc` and `ai` all carry `@stability unstable`, which by the project's own definition means they may break in a *minor* release.

**Effect Cluster and Workflow do durable execution on Postgres, but as a durable mailbox rather than a step journal.** Persisted RPCs are written to `cluster_messages` / `cluster_replies` before handling; a workflow is a cluster entity keyed by a hash of its name plus idempotency key, and every activity, deferred and timer is a persisted message. Delivery is at-least-once with opt-in persistence per RPC. You can run all of this on one machine via `SingleRunner.layer`, which still requires a `SqlClient` and uses advisory locks for shard ownership — the same mechanism your journal already uses.

**For a solo developer whose code is mostly agent-written: adopt Effect as the runtime around your journal, not as a replacement for it — and do not rewrite the existing platform.** The highest-value parts (typed errors, `Schedule`, `Layer`, `Schema`, `@effect/sql-pg`, OTel) are the stable ones and are exactly what makes agent-generated code checkable. The durable-execution parts duplicate what you already own, are the least settled, and put a queryable `runs`/`steps` schema behind encoded blobs.

## What breaks moving from 3.x

The migration guide is explicit that the programming model is unchanged and the churn is in packaging and detail:

- **Packages consolidated.** `@effect/platform`, `@effect/rpc`, `@effect/cluster` and friends now live in `effect`. What remains separate is platform-, driver- and provider-specific: `@effect/platform-*`, `@effect/sql-*`, `@effect/ai-*`, `@effect/opentelemetry`, `@effect/atom-*`, `@effect/vitest`. Version numbers are now lockstep, so `effect@4.x` pairs with `@effect/sql-pg@4.x`.
- **Module paths moved.** `effect/unstable/http` → `effect/http`, `effect/unstable/ai/LanguageModel` → `effect/ai/LanguageModel`, with **no compatibility exports**. Note that the doc mirrors still show the old `effect/unstable/*` paths in places (pages dated 30 May 2026), so inherited snippets may not compile.
- **Renames that bite everywhere:** `Context.Tag` → `Context.Service`, `FiberRef` → `Context.Reference`, `Runtime<R>` removed, `Schema.transformOrFail` → `Schema.transformEffect`, `catchAll` → `catch`, `unsafeCoerce` → `cast`, many `Option`/`Array` methods renamed to return `undefined` instead of `Option`.
- **Semantics:** flattened `Cause`, changed `Effect` subtyping, automatic fiber keep-alive (process lifetime management), and layer memoization across `Effect.provide` calls.

Add the fact that **unstable modules really do break in minors**: 4.1.0 replaced `effect/Crypto` with per-family `effect/crypto/*` services and, as a result, `SqlMessageStorage` and `SingleRunner` now take `Digest.Digest` instead of `Crypto.Crypto`. A patch-level upgrade of your cluster layer can therefore change its provider requirements. Pin exact versions.

## What you actually get

**Typed errors.** `Effect<Success, Error, Requirements>`. Errors are `Schema.TaggedError` classes, so they are also serialisable and pattern-matchable; `catchTag`/`catchTags`/`catchReason` give exhaustive handling, and defects are separated from expected failures. This is the single biggest lever for AI-written code: a wrong error model fails `tsc`, not production.

**Structured concurrency and fibers.** Forked children are scoped to their parent and interrupted with it; `Effect.all(..., { concurrency: n })` bounds fan-out; `FiberSet`, `FiberMap`, `FiberHandle` cover the supervision patterns you would otherwise hand-roll. v4 rewrote the runtime: the release claims a minimal program at 7.1 kB vs 35.6 kB, 4.57M concurrent tasks/s vs 0.71M, and 86% less heap for 50,000 fibers (medians of nine runs, self-reported).

**Schedule.** Exponential, spaced, cron, jittered and intersected schedules as values, retryable via `Effect.retry`, and testable under `TestClock` without sleeping. For an orchestration service this alone replaces a lot of bespoke retry bookkeeping.

**Layer DI.** Typed service construction with `Layer.provide`/`provideMerge`, `LayerMap` for per-key resources (one pool or one sandbox per tenant), and layers memoized by identity in 4.x. The catch is real: layer wiring errors appear as missing-requirement type errors that read badly, and this is a common complaint from newcomers.

**Schema vs zod.** Schema is a codec library, not just a validator: decode *and* encode, transforms in both directions, JSON Schema generation, arbitraries for property tests, equivalence, optics, `StandardSchemaV1` interop. Effect's own benchmark (run against the public `schema-benchmarks` suite) puts create-schema at 60.1 µs vs Zod 4.6.2 at 83.7 µs, parse-valid at 5.03 µs vs 7.01 µs, but typed-codec decode at 0.106 µs vs Zod's 0.043 µs — so Zod still wins on warm codec paths. Zod is at 4.6.7 and has `z.compile()` for precompiled parsers, which widens that gap. Practical read: Schema is better at *boundaries that must round-trip* (RPC payloads, workflow payloads, DB rows); Zod is fine and already in your codebase, and Effect can consume Zod schemas through Standard Schema.

**`@effect/sql-pg`.** In v4 the Postgres client is "backed by the native wire protocol client" — no `pg` dependency — with pooling (`maxConnections`, `minConnections`, `multiplex`, `acquireTimeout`, `onAcquire`), `SqlClient` transactions, `SqlResolver` for batched/deduplicated lookups, `Migrator`, and `SqlSchema` for deriving codecs from queries. Unstable, because it exposes driver options.

**`@effect/opentelemetry`.** A thin layer (`NodeSdk.layer`) that installs your existing OTel processors/readers into the Effect runtime. Core also now ships OTLP exporters, a Prometheus metrics module and `OtlpResource`, so a greenfield service may not need the package at all. Unstable for the usual third-party-type reason.

**`@effect/platform-bun`.** `BunRuntime.runMain`, `BunServices`, and cluster transports `BunClusterSocket.layer({ storage: "local" | "sql" | "byo" })` and `BunClusterHttp`. Bun is a first-class target in the release notes but still visibly second in line — e.g. a recent week's fixes included "Bun WebSocket interruption on close" and "Default Bun idle timeouts to off".

**`effect/ai`.** `LanguageModel` service (`generateText`, `generateObject` against a Schema, `streamText`), `Tool`/`Toolkit`, prompt/response/tokenizer models, `McpServer` and a native `McpClient` (experimental). Providers live outside as `@effect/ai-openai`, `-anthropic`, `-openrouter`, `-cloudflare`, `-typesafe`. Unstable. If your factory drives coding agents over HTTP/CLI rather than through model SDKs, this is optional.

## Durable workflows on Postgres, concretely

There is no separate workflow database. `ClusterWorkflowEngine.layer` implements the ordinary `WorkflowEngine` service on top of **sharding plus message storage**, so "every execution, activity, deferred completion, resume, interrupt, and durable clock wake-up is a persisted cluster entity message keyed by workflow name and execution ID."

Mechanics worth knowing before you commit:

- **Persistence is opt-in per RPC** via `.annotate(ClusterSchema.Persisted, true)`. Unannotated messages are volatile: serialised, sent to the owning runner, lost if it dies.
- **At-least-once, not exactly-once.** A persisted message stays in the mailbox until a terminal reply is recorded; a crash mid-handler means redelivery. Deduplication uses a `PrimaryKey` on the payload; `ClusterSchema.WithTransaction` wraps handling in the storage transaction. The project's own Cluster series walks through the dual-write problem and why idempotency keys (plus, in the workflow case, the deterministic execution ID) are what make replay safe.
- **Replay is re-execution.** On resume the handler re-runs from the top and activities short-circuit to their persisted results. The body must therefore be deterministic outside activity boundaries — no randomness, no clock reads, no ambient state in names. Changing a persisted name or schema "is a migration, not a refactor".
- **Suspension is a value, re-driven on a schedule.** Blocking on a deferred, child workflow or durable clock returns `Suspended` instead of holding a fiber, and the engine retries suspended executions on `suspendedRetrySchedule` — exponential from 200 ms capped at 30 s. For a workflow that sleeps three days waiting on a human, that is a poll loop against the database unless the durable-clock timer path short-circuits it; worth measuring before you put week-long agent sessions on it.
- **Storage shape.** `SqlMessageStorage` creates `cluster_messages`, `cluster_replies` and `cluster_migrations` on startup and stores encoded envelopes and reply chunks. Contrast with your `runs`/`steps` tables: you cannot `SELECT` a workflow's current step. Inspecting a run means decoding messages or calling `poll`/`resume` through the engine.
- **Backpressure.** An entity's mailbox capacity defaults to 4096 outstanding messages, and messages held without a reply count against it; overflow fails with `MailboxFull`.
- **Single node is supported.** `SingleRunner.layer({ runnerStorage: "sql" | "memory" })` provides `Sharding`, `Runners` and SQL-backed `MessageStorage` with no-op runner communication and health, explicitly "for local, embedded, or small single-node setups". It requires `SqlClient` and `Digest`, and its `ShardingConfig` exposes `shardLockDisableAdvisory`, `shardLockExpiration`, `shardLockRefreshInterval`, `refreshAssignmentsInterval`, `entityMailboxCapacity`, `entityMessagePollInterval` — i.e. advisory-lock leases with refresh, which is architecturally the same thing you already built.

So: **production-usable, single-node-viable, but not a thin wrapper over your existing design.** It is a full actor system whose durability happens to land in Postgres.

## Production reality

**Adoption is real.** Almost 66M weekly downloads, named production systems (OpenCode, OpenRouter, MasterClass Cortex, Datapizza), and a stable 4.0 with an LTS policy — the version-churn objection that dominated 2024–25 commentary is now largely answered.

**Cluster has had real incidents.** A production report described SQL-backed workflow consumption stalling after a rolling deploy while runners stayed healthy — messages unprocessed, `last_read` frozen, only the log line "Could not find entity manager for address, retrying". It was fixed in Oct 2026, months after being filed. A separate report had `BunClusterSocket.layer({ storage: "sql" })` on Bun 1.3.10/Postgres 17 register runners and receive shard assignments but never reach entity registration; it was closed as not-planned after the reporter could not reproduce on newer v3 builds, with maintainers noting SQL shard-lock fixes had landed. Most recently, on **`effect@4.0.6`**, sequential runner joins during a rolling deploy moved the same shard several times, draining and replaying entities on each move; that shipped a `runnerJoinDebounce` option in 4.1.0 — **defaulting to 0, i.e. current behaviour preserved**, so you must opt in.

That pattern — plausible, well-diagnosed cluster bugs, fixed quickly but shipping as opt-in changes in a module that can break in a minor — is the honest maturity signal. Not abandoned, not boring.

**The complaints are consistent and mostly about cost of comprehension, not correctness.** From the 4.0 Hacker News thread and a production write-up: learning curve compared to RxJS and called "brutal" when teaching a team; debugger stepping lands you in Effect's internals rather than your logic, and "execution flow is not obvious"; `Effect.forEach` and `runPromise` read worse than `for...of` and `await`; the docs' AI-flavoured prose gets mocked; and one solo developer concluded he'd "have a really hard time suggesting this technology at work" because it assumes an FP background most TS devs lack. Counterweights in the same thread: people shipping three projects on the beta "totally pain-free", claims that v4 stops you fighting the type system, and the observation that the call site of `runX()` is a clean boundary so you can adopt incrementally. Notably, the loudest complaints are from people who used it; the dismissals ("it's for people who want to write OCaml in TypeScript") are from people who did not.

**Performance.** The published figures are 3.x vs 4.x only, self-reported with a stated methodology. I found no independent benchmark of Effect against plain `async`/`await` for equivalent logic, so treat "runtime overhead is minimal" as a claim, not a measurement. In practice the fiber runtime is unlikely to be your bottleneck in an orchestration service that spends its life waiting on Postgres and LLM streams; the cost that will bite is memory/serialisation behaviour of the cluster mailbox under backlog.

**Debugging is better than its reputation but not solved.** Spans are automatic with `Effect.fn("name")`, `Cause.pretty` gives real stack traces for failures, and there is a `devtools` module for inspecting fibers. But a retry schedule is still less legible than a `for` loop, and `Cause` output is verbose enough that agents and humans both skim it.

## LLMs writing Effect

Evidence on both sides, and the balance is "workable with scaffolding, bad out of the box".

For: the package ships the maintainers' own `AGENTS.md` / `LLMS.md` plus executable examples under `ai-docs/`, with concrete house rules (prefer `Effect.gen`; use `Effect.fn("name")` when a span helps and `Effect.fnUntraced` in hot paths; never write a function whose body is only `return Effect.gen(...)`; `return yield* new SomeError(...)` so TypeScript sees termination; all validation through Schema). The site markets "LLMs ❤️ Effect" on the argument that a declarative API plus a typed feedback loop gives agents something to self-repair against. The migration post even says to hand the migration guide to your coding agent.

Against: v4's API surface postdates essentially every model's pretraining. A fine-tune published on Hugging Face exists *specifically* because "its exact API surface is absent from base models, so they hallucinate v3" APIs — the card targets `effect@4.0.0-beta.80`. Community harnesses converge on the same workaround: keep a shallow clone of the Effect source in a cache and make the agent read it instead of guessing. And the surface is enormous — one independent audit counts 143 modules exported from the root barrel plus 251 modules across 22 `effect/<area>` families.

The realistic failure mode is not "agent writes nonsense"; it is **plausible v3-flavoured code that type-checks against nothing** — `Context.Tag` instead of `Context.Service`, `catchAll` instead of `catch`, `effect/unstable/cluster` paths, `@effect/platform` imports. Second failure mode is subtler and worse: an agent puts a `Date.now()`, a random id, or a direct `fetch` *outside* an `Activity` inside a workflow body. That compiles, runs, passes tests, and silently breaks replay after the first resume. **Replay determinism is a runtime property Effect cannot type-check.** You would own that review burden.

## Effect vs plain TS + Zod + your journal

Your journal is: `runs` and `steps` tables, advisory-lock leases, replay by step id, Zod at boundaries, OTel already wired. Effect's corresponding offer is: the same idea, encoded into `cluster_messages`/`cluster_replies`, keyed by entity address, with an actor runtime and sharding on top.

**What Effect genuinely buys you, ranked by value per unit of risk:**

1. **A typed error channel that agents cannot ignore.** This is the strongest argument. With plain TS, an agent's forgotten `try/catch`, swallowed `unknown`, or invented error shape is invisible until runtime. With `Effect<A, E, R>`, a wrong error model or a missing dependency is a compile error at the call site. For code mostly written by agents, the type system becomes your reviewer.
2. **`Schedule` + structured concurrency** replacing hand-rolled retry/backoff, cancellation trees, and orphan cleanup — precisely the bugs your journal will hit as sessions get longer.
3. **Per-key serialisation via entities** instead of ad-hoc advisory locks. "One live owner per issue id, messages serialised, passivated when idle" is a better mental model than "acquire lock, renew, hope". This is the part of Cluster I would actually want, and `SingleRunner` gives it without multi-node operation.
4. **Schema as a codec** for RPC/workflow/DB boundaries, plus JSON Schema for free — which matters when the payloads are agent-produced.
5. **One dependency-free install** with lockstep versions, and OTel spans by default.

**What it costs you:**

1. **The journal stops being queryable.** Your `runs`/`steps` tables are the operational UI: you can see where a run is, count stuck steps, and write a one-line SQL fix. Workflow state is encoded messages behind an engine API.
2. **An unstable dependency under your most critical invariant.** 4.1.0's crypto change is the concrete proof that a minor bump can alter how `SqlMessageStorage`/`SingleRunner` are constructed.
3. **A large surface for agents to be wrong about**, with docs mirrors still showing pre-4.0 import paths.
4. **Operational surface you did not ask for**: shards, runners, shard locks, mailbox capacity, join debouncing. Your advisory-lock journal has one moving part.

**The decision rule I'd apply.** Durable orchestration is only worth replacing when the replacement removes work you are actually doing badly. Right now you have working lease+replay semantics and a schema you can inspect; what you do not have is a good story for cancellation trees, bounded concurrency across many agent sessions, scheduled retries, per-issue serialisation, and typed failure propagation across service boundaries. That is exactly Effect's core strength, and none of it requires Cluster.

So, concretely, for the new "factory":

- **Phase 1 — Effect core + your journal.** `effect` for `Effect`/`Layer`/`Schema`/`Schedule`/`Stream`, `@effect/sql-pg` for Postgres, `@effect/platform-bun` for runtime, `@effect/opentelemetry` to bridge your existing OTel. Keep `runs`/`steps` and the advisory locks. Every step is still a row; every side effect is still a `step` with an id; the journal stays the source of truth and stays greppable. Pin `4.1.0` exactly.
- **Phase 2 — add entities, not workflows.** If per-issue serialisation hurts, put `Entity` + `SingleRunner` in front of the journal for the in-memory coordination, and keep the journal as the durable record. This is the middle path almost nobody writes about, and it is the one that fits a single-node solo deployment.
- **Phase 3 — only then consider `effect/workflow`.** Move to `Workflow`/`Activity`/`DurableClock` if you want to delete the journal, you accept that run state becomes messages, you can live with `Suspended` re-drive polling, and you are willing to keep a replay-determinism test suite plus a version-pinning discipline. If you get there, `SingleRunner.layer({ runnerStorage: "memory" })` with SQL message storage is the right topology — do not stand up multi-runner Cluster for one person.

**What I would not do:** rewrite the existing platform in Effect. Its journal is already the thing Effect would replace, the code works, and a migration of a running system is the single highest-variance way to spend agent hours. The migration guide's optimism ("hand it to your coding agent, and it should do most of the work") is about mechanical renames, not about re-deriving your durability semantics.

## What stays uncertain

- **No independent performance measurement** of Effect against plain async/await for equivalent programs. The 6.4×/~86% figures are Effect 3 vs Effect 4 on Effect's own harness.
- **No public production case study specific to Cluster or Workflow.** The named adopters are for Effect generally; the Cluster evidence I found is bug reports, not deployments.
- **Whether the `runnerJoinDebounce` fix (4.1.0) is sufficient.** It defaults to `0`, so out-of-the-box behaviour on a rolling deploy is unchanged until you tune it.
- **Bun + Cluster at scale is unproven in public.** One detailed failure report, closed as not-planned; several Bun-specific fixes in recent release notes. No evidence of large Bun cluster fleets.
- **The exact current import paths and API shapes for workflow/cluster.** Doc mirrors I read carry 30 May 2026 pages and pre-final `effect/unstable/*` paths, while the migration guide says the `unstable` segment was dropped. The pinned handbook is the more reliable reference; verify against `node_modules/effect` for anything you copy.
- **The `Suspended` retry schedule's real cost** for multi-day sleeps is unmeasured here; it is documented as exponential-to-30s re-driving, but I could not confirm how much a `DurableClock` timer short-circuits it.
- **No controlled study of LLM accuracy on Effect v4.** The evidence is model cards, skill repos, harnesses and anecdotes.
