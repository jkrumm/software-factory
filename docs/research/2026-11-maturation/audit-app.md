# Audit: use-case and wiring layer (apps/server app, main.ts, api, adapters, settings)

Scope read-only. Evidence = file:line from rg/sed/wc at master 8fa0a18c. Nothing was executed (no make, no tests). The deployed env file (~/.config/factory/env) was NOT read, so "is it set in production" is unverified everywhere below; only code, the allow-list (scripts/env-file.sh), the tpl files and the test trees were used.

## 0. Answers to the seven questions (short)

1. main.ts is 1164 lines, of which main() is one 1002-line function (apps/server/src/main.ts:161-1164). It hand-builds: 13 stores inside one unit of work (:187-201), 10 settings loaders (settings.ts, leads, loops, planning, intake, uptime, otel, checkpoint, console, needs; loadNeedsSettings is called twice, :279 and :1074), about 35 adapters/ports, 20 LoopSpec literals (:402-915), 2 extra self-paced pollers (:1120-1123), 2 HTTP listeners, a 9-step shutdown. There are four composition styles: inline in main.ts (loops, checkpoints, quality/ship, host/reaper, health, console), five compose-*.ts files (intake, issues, leads, planning, read; 108/50/172/215/14 lines), factory functions that return use-case bags with forwarding lambdas (checkpointUses, app/checkpoints-uses.ts:30-66, 28 one-line forwarders), and API-port interfaces (IssueApi, PlanningApi, CapacityApi, LeadRoutes, IntakeApi, QualityWrites, LoopsApi, ReadApi, ReadModelDeps in api/app.ts:30-52) filled by lambdas. What shrinks it by two thirds without DI: put each LoopSpec next to its pass (see finding 5), and stop passing repeated closures (five copies each of `file: (body) => intake.api.file(body,'agent')`, `locate: (repo) => repos.locate(repo)`, `token: intakeEnv.github.token`; main.ts counts).
2. Loops share one runner shape (app/loops/runner.ts: interval, single-flight, kick on change, last pass recorded in loop_passes) but not one pass shape: 15 of 20 specs in main.ts repeat the same 4 lines (`const pass = await xPass(...)`, `if (!pass.ok) return pass`, `said('x', pass.value.problems)`, `return ok(xSummary(pass.value))`). Nine loops run at the 10 s default tick (leads, planning, watch, settle, send, steward, triage, queue, friction: app/loops/settings.ts:166-168, 199-219). Of those, friction decides "not due" itself (app/loops/friction.ts:59-73: one DB read per tick plus a closed-issue count query each tick while no clock trigger), and its own record (lastFrictionPassAt) duplicates the runner's lastPassAt. desk (interval 15 min) and hygiene (min 15 min) also hold their own "due" ledgers (desk.lastPassAt, hygiene pass records). Three schedulers exist: LoopRunner (20 loops), selfPaced (adapters/intake/schedule.ts: github intake, launchd intake, uptime, otel, via compose-intake.ts:97-101 and main.ts:1121-1123, invisible in the loop view), and read/health-probe.ts's own timer.
3. Settings: 175 distinct FACTORY_* names in tracked non-doc code, 162 read by src; 122 on the allow-list; 40 not (secrets, CLI/slot client vars, launcher vars). 37 allow-listed names appear in no test (apps/server/test, tests/, scripts/test, packages) and in at most 3 doc files: pure tuning knobs listed in finding 7. 12 hand-written zod+safeParse+"issues.map(...).join('; ')" loaders (rg count). LeadSettings.tickMs is dead (finding 1).
4. app/ splits: leads-*.ts (12) is a real decomposition of one tick (leads-tick.ts is the only importer of finalize, follow, held, quiesce, outbox); checkpoints-*.ts is a decomposition by loop step, imported only via checkpoints-uses.ts and main.ts; capacity-*.ts and planning-*.ts are glued only by compose-planning.ts. These are accretion by feature, not wrong, but 7 files are pass-through or under 40 lines (list in finding 10). The real depth problems are the single-function giants: createIntake app/intake.ts:237 (1278 lines, 36 inner functions), main() 1002 lines, postgresCheckpointStore adapters/postgres/checkpoint-store.ts:423 (858 lines), checkpointRoutes api/checkpoints.ts:238 (681), postgresCapacityStore :132 (520), readModelRoutes api/read-models.ts:156 (460), postgresLoopStore (463), githubPoller adapters/intake/github.ts:204 (382). Measured by a crude top-level span scan; nesting depth was not measured (unverified).
5. Leftover scaffolding: see findings 2, 6, 8. About 267 hits for for-now/legacy/old core/cutover/rollback-type words in apps/server/src, apps/cli/src, packages/*/src, most are plain "old process/old tree" prose; the real ones are listed.
6. Error handling: 238 catch sites in adapters+app, 165 empty `catch {`/`.catch(() => x)`, 17 hand-written `catch -> return err(portError(...))`, 53 copies of `error instanceof Error ? error.message : String(error)`. "Every port returns Result" is not true: readers like friction/evidence/closedSince, host snapshot, processTable, lightGate, reviewerTakesAll are throwing or nullable and each caller wraps them (app/loops/friction.ts:62-69, 99-135; app/capacity-aim.ts:34; app/leads-held.ts:45; app/leads-start.ts:256,273; compose-leads.ts:84). unitOfWork.inTransaction() exists for exactly one assertion (app/outbox.ts:62) and costs an AsyncLocalStorage on every transaction (adapters/postgres/unit-of-work.ts:17-19).
7. Adapters: five independent Bun.spawn + timeout + kill implementations, four of them named runProcess (finding 3); GitHub REST reads re-implemented in selfwatch/github.ts (finding 4); about 135 `const XRow = z.object(...)` plus hand mapped snake_case to camelCase `xOf` mappers across 10 store files, every row zod-parsed on read (rg count; adapters/postgres/capacity-store.ts:23-128 is typical). Stores live in four places: adapters/postgres/ (9), adapters/quality/store.ts, adapters/leads/store.ts, adapters/intake/store.ts.

### F8. Friction polls every 10 s; schedule and "due" are decided in two places
- Evidence: friction interval = tick (loops/settings.ts has no friction branch, so 10 s default); frictionPass reads lastFrictionPassAt and, when no clock trigger, `closedSince` (read/retro-outcomes via main.ts:659) each tick (app/loops/friction.ts:61-70), returning `not due` (:181).
