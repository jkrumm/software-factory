# Architecture: what is built

**A modular monolith on Bun: plain TypeScript and zod, Postgres as the only store, domains with no I/O behind ports,
Elysia at the edge, and a generated CLI.** It has been the running factory since the cutover of 2026-11-08
(`docs/rewrite/state.md` is the log of how it got here). Words follow `docs/language.md`; the rules a change must keep
are in `AGENTS.md`; why something is as it is, in `docs/decisions.md`. This page says where things are and how they fit.
What is not built is the last section.

## Layout

```
apps/
  server/     Elysia app: domains, application services, adapters, read models; migrations in apps/server/migrations
  door/       the alert door: loopback, one token (`machine`), posts alerts and refusal reports to the server
  cli/        `factory`: commands generated from the OpenAPI document, plus the hook, slot, deploy-lock, merge-lock, follow, role and issue schema verbs
  console/    the Console: a Vite and React PWA (shadcn on Base UI, Tailwind 4 with Basalt tokens, TanStack Router and Query); the server's second listener serves its build
packages/
  contract/   zod schemas: every request, response and event; the OpenAPI source; the spool format the hook shares
  client/     typed client (Eden) and the CLI's transport, including the change-stream follower
  accounts/   the Claude Code subscription picker and the `claude-account` CLI (`docs/accounts.md`): a pure rule over ports, no server or database (the server reads it in-process: `adapters/planning/accounts-source.ts`), one file buildable for a machine without a checkout
tests/
  scenarios/  use cases run against a real server and Postgres with fake hc and agw: the acceptance suite
  e2e/        Playwright against a seeded server: every Console screen, and the source of the README's screenshots
integrations/ the client pieces other machines install: the Claude Code hook entries, the Herdr glance mod, rd's contract, the Hermes fleet skill
config/       roles.json (tier and effort per role), infra.json (host to repo, for incidents), throughput.json (the counting epoch)
scripts/      deploy, verify, launch, env-file, merge-guard, the checks of the build (boundaries, retired words, vocabulary, public scan, README)
deploy/       LaunchAgent templates
docs/         product, language, architecture, operations, decisions, plan format, research, evidence
```

## The server

```
apps/server/src/
  kernel/        Result, ids, clock, keys, the event envelope, agw call types. Imports nothing else
  domains/       pure: types, rules, state machines, ports (interfaces). No I/O, no SQL, no Elysia
    intake/        signal envelope, trust and routing rules, fingerprints, incidents, the incident correlation
    planning/      projects, plans, the chain, queue order
    capacity/      accounts and windows, memory, load, repo claims, queue state, test slots, admission
    work/          the Issue: events, the total transition table, effects, the generated diagram
    leads/         attempts, the brief, notes, session state derived from hook events, the stop rule
    quality/       the ship gate, evidence, the watch and verify
    checkpoints/   Decisions, artifacts and revisions, errands, the owner's pages
    loops/         what the steward and triage decide: stall rules, settling
  app/           use cases: one transaction to claim, the port call outside it, one to record
    loops/         the loop runner and the steward and triage passes
  adapters/      postgres stores, hc terminals, agw, git, ntfy, filesystem blobs, the intake pollers, the hook socket, the uptime poller (`adapters/uptime/`: Argo's Kuma snapshot, `uptime` of `GET /v1/overview`: up, down, total, at most 10 down names, null when `FACTORY_UPTIME_URL` is unset, never read or older than 10 min; `FACTORY_UPTIME_TOKEN`, `FACTORY_UPTIME_EVERY_MS` default 60 s), the metrics export (`adapters/otel/`: the queue by reason, slot waits by reason and repo, step placements, seats per account and the load beside its ceiling, from `read/capacity-gauges.ts`, as OTLP/HTTP JSON gauges to ClickStack every `FACTORY_OTEL_EVERY_MS` (60 s) over the last `FACTORY_OTEL_WINDOW_MS` (5 min); off without `FACTORY_OTEL_ENDPOINT`, a failed push is one log line and touches no loop; `FACTORY_OTEL_ENDPOINT` and `FACTORY_OTEL_KEY` are refs of `.env.server.tpl`)
  api/           Elysia route groups, auth and the caller policy
  read/          read models (SQL projections) for the API and the stream
  compose-*.ts   wiring of each domain; main.ts boots, takes the process lock first and shuts down in order
```

**Rules, enforced in `make check` by `scripts/boundaries.ts`:**

- `domains/*` import only `kernel` and their own folder. A domain reaches another only through `app/`.
- Each domain owns its tables. `read/` crosses them and is read-only.
- A port is an interface in its domain; an adapter in `adapters/` implements it; tests use fakes of the same interface.
- Only the unit of work, the migration runner and the read models' bounded read (`read/bounded.ts`: read-only, with a statement timeout) open a transaction. A port is never called inside one: claim,
  commit, call, record.
- Every port returns `Result<T, PortError>`; only a programming error throws. `PortError.kind` is `timeout`, `gone`,
  `refused` or `unreadable`.
- An intake poller reads the outside world and hands signals to the sink; it touches nothing else of the server.
- `apps/cli/src/hook.ts` imports only `node:fs` and the spool half of the contract.

## The Issue machine

States (stored; screens show the five words of `docs/language.md` "Where work stands", `workOf` in `packages/contract/src/work-words.ts`: Running, Paused, Ready, Held, Checking, and Planned for plan rows; `scripts/vocabulary.ts` fails `make check` on a state word in a screen's text): `settling`, `queued`, `working`, `waiting`, `watching`, `closed`. `apply(state, event)` is a total table in
`domains/work/table.ts`: every `(state, event)` cell is written down as a transition with its effects, a named refusal
or a named ignore, and a missing cell fails `tsc`. The diagram and the wait table in `docs/language.md` are generated
from that table.

- **One writer.** `app/` stores the event, the new state (`UPDATE … WHERE id = $1 AND version = $2`) and the effects in an
  outbox in one transaction, then the outbox runs the effects (`app/outbox.ts`): claimed with a lease, retried with a
  doubling delay. A late event that names an old attempt, watch, wait or checkpoint is ignored or refused by the table.
- **A review wait takes Decisions.** While an Issue waits for the verdict on a Concept or Spec, the lead may raise and amend
  Decisions about it (`wait.decisions`, each linked by `decisions.artifact_id`; the steward's ask stays stall-only). The wait
  keeps its `since` and `told`, and ends when the verdict is given and every such Decision is settled, in either order
  (`verdictGiven` marks a verdict that came first): one `note_lead` then covers the verdict and the answers. Needs lists
  the Decision with its `artifact`, and the review item only until the verdict is given.
- **Model test** (`apps/server/test/work/model.test.ts`): a seeded generator plays random event sequences and checks
  invariants: a machine wait always has an exit that needs no person; a wait on the owner always states what it holds (a review wait with Decisions open leaves in steps: the verdict and each answer); a
  closed Issue reopens only by its verb, within 30 days.
- No XState, no workflow engine. Events in Postgres plus a row version are the whole mechanism (NL11).

## Signals and triage

Every input is one envelope (`source`, `kind`, `origin`, `trust`, `repo`, `fingerprint`, `title`, `text`, `link`) and goes
through `receive` in `app/intake.ts`; the answer is a triage outcome (`docs/language.md`).

- **Sources.** The owner (`factory signal`, Hermes through the narrow `signal` caller as `owner:hermes`), agents
  (`agent:<repo>`), the alert door (Kuma and HyperDX), and two pollers: GitHub (the owner's new issues and failing
  checks, a failing one filed as an `incident` so it takes the fix's place beyond the repo's `leads` and the lead of every
  other Issue of the repo with an open pull request is noted once; anyone else's need the label and are held) and launchd (a
  LaunchAgent's state). Infra alerts (memory, disk, load, swap, silent hosts, containers) are ClickStack alerts through the door (A4), not a poller. `repo` comes from the route, the door registry or the caller, never from an outside payload.
  **App feedback** is a door source of its own: `POST /feedback/<app>` with the app's token (`feedback-<app>` in the door's
  tokens file) becomes `POST /signals/feedback`, one envelope for every app (`FeedbackRequest`: app, version, route, title,
  text, link). It is a signal from `feedback:<app>`, trust `outside`, whose text opens with an `app/version/route` header;
  the repo is the door route `(feedback, <app>)` or none, and the fingerprint is the repo (or app) and the title, never the
  version or route, so one complaint from two builds is one.
  **A monitor with no route** is counted, and the settle pass deals with it without the owner: one whose name says a
  project (`domains/intake/place.ts`: the project name is a run of the monitor's words, the longest and only match) or
  that has a `<name> - Push|Door` sibling routed gets that route (`set_by` `factory:name`), up or down; one down past
  10 min with no place is filed in `FACTORY_HOME_REPO` when set, else, past `unroutedHeldMs` (6 h), held once as a signal
  with no repo (the owner or the Judge promotes it with one). Setting a route for a monitor that is down files its last
  alert in that repo (Kuma notifies on a change only) and answers the held signal.
- **Backlog sweep.** With `FACTORY_GITHUB_BACKLOG=1` the GitHub poller's first pass after a start also reads every open issue
  of each polled project (oldest first, pull requests out) and files it through `receive`: the label's and the author's as
  `machine`, everyone else's `outside` (held). It carries `writeback: false` and no `admitted`, so nothing is ever written to
  GitHub for it (promoting a held one keeps that); one `github backlog:` log line per issue says the outcome. A replay is idempotent (the subject and event keys), and a sweep
  that could not read a repo whole runs again on the next pass. Unset it after the sweep.
- **Who may file where.** `domains/intake/rules.ts` gates a signal: a work repo hears only the owner (NL18), an unknown
  repo hears no one, and a project hears the automatic sources its `signals:` lists. The door's are routed.
  One exception to the work-repo rule: a lead's signal (`from agent:<its repo>`, `filer` set by the CLI) whose own Issue the owner filed (origin `you`) is held, not dropped, so the owner can promote work it owes a work repo; any other agent signal there is dropped (`work_repo`). The `screen` loop never reads such a signal (a work repo's words go to no workflow, and the last look never dismisses it): it stays held in Needs you.
- **Incidents.** Alerts of the monitoring sources on one host or dependency inside a window join one incident: the VPS
  down fires HyperDX (its infra and app alerts) and Kuma, and there is one Issue. The window is a setting (`FACTORY_INCIDENT_WINDOW_MIN`).
- **Amend or new.** A loop's finding (friction, hygiene, selfwatch, throughput: `intake.api.file` with a `LoopFinding`) is
  matched by its key alone (loop, class, repo, subject; `findingKeyOf`, a subject row `finding:…`): an open Issue of
  that key takes it as a note, one closed within the fingerprint window counts it as a repeat, else it files anew; no
  title match and no workflow call (an open Issue filed before the key existed is taken over once by its title's
  fingerprint), and an agent's own signal is never matched or offered for amending to an open Issue a finding filed. An
  amend by title match or workflow keeps a subject row for the signal's fingerprint, so the same words again are a repeat.
  A repeat of a fingerprint inside its window changes nothing. A signal that carries the retro marker (`Retro: <date> kpi=…`, the last words of its text) is one recommendation with its own number to move: it skips the title match and the workflow and files its own Issue (only its own fingerprint folds it into an open one). An owner or agent signal that matches an
  open Issue clearly (title overlap) amends it and reaches its lead as a note. Otherwise, unless a fingerprint, subject or
  open incident already settles it, the `factory-triage` workflow sees the repo's open Issues and those closed in the last
  day (outcome, reason) and answers amend `<open Issue>`, "already settled: `<closed Issue>`" or neither (file anew): a
  settled answer acks `dropped`/`settled` and stores the signal dismissed by the judge, for a person's request and for a
  `down` alert alike. The request waits for the workflow at most `triageWaitMs` (8 s, under the client's 10 s): later, or never (the line is down), it files anew and the run goes on unwatched; the same signal sent again rejoins it by its key. `POST /signals` therefore answers from the local database whatever the network does. The workflow side (agent-workflows `factory-triage`) must learn `settled`; until it does the extra
  input is ignored and `settled` never comes back, which is today's behaviour. A `down` waits out a heal grace as `held`: an `up` inside it makes it `healed`, and a project's heal rule runs
  `make restart` in its repo (`adapters/intake/runbook.ts`, outside any transaction) before an Issue is filed.
- **Quarantine.** An outside signal is held and reaches a lead only when the owner or the Judge promotes it, fenced as data.
  Promoting keeps a subject row for the signal's fingerprint (as for a person's request). A later outside signal with that
  fingerprint from the same source amends the promoted Issue while it is open (a `noted` event, fenced; the signal is stored
  `amended`, once per distinct text); when that Issue is closed it is held again as new, and while a signal is still held a
  duplicate is that held signal (`replayed`, no second row). A held signal can also be **dismissed** (`POST /signals/:id/dismiss`,
  the owner or the Judge, a reason of 1 to 500 characters): state `dismissed` with `dismissed_reason`, `dismissed_by`
  (`owner`, `judge` or `probe`) and `dismissed_at`, no Issue, and it leaves Needs you and the friction count. Only a held
  signal can be dismissed or promoted; a later signal with a dismissed one's key is a new report, held under that key extended with the dismissed id (and so on down the chain). A **probe** (`probe: true` on `POST /signals` or the door's feedback, carried on the
  `Signal` envelope) passes the loop guard, the work-repo rule and the trust gate as any signal does, then is stored
  `dismissed` by `probe` under a key of its source and fingerprint (a replay stores once): it files nothing, is never held and
  never reaches the triage workflow; its ack is `dropped`, detail `probe`.
- **Screen.** The `screen` loop (below) has the Judge look at held signals. Prompt injection: the workflow's verdict can only
  promote, dismiss or leave the one signal it was shown (a `leave` stores `screen_note`, `screened_at`; the Console shows it as
  "Judge: ..." above Promote and Dismiss); a promote files an Issue whose text is still outside text, fenced as data in the
  lead's brief, as the owner's promote does. A newly held signal waits for the next pass (no kick; the interval is
  `FACTORY_LOOP_SCREEN_MS`, 10 minutes at least).
- **Loop guard.** A change a loop made never fires that loop again.
- **Stop the line.** While a repo's alert is unsolved, only its fix is admitted.

## Capacity and leads

- **Admission** (`domains/capacity/admission.ts`) is pure and decided again at every claim, in this order: queue state
  (`drain` starts nothing), the project's **doctor** (kind `doctor`, `domains/capacity/doctor.ts`, `adapters/doctor/`: `doctor: make doctor` in a `project.yaml` is a
  read-only command of seconds that exits 0 when this host can run the project and otherwise exits non-zero with one line per missing prerequisite and its fix;
  it runs in the project's own checkout under a 60 s timeout, a red reading stands 5 min and a green one 1 h, one run per project at a time, kept in memory so a restart asks again;
  while it is red every Issue of the project stays queued, the reason `<project> cannot run on this host: <first four lines>`, and the hygiene `check` probe is skipped with the same words,
  so a project needs no `hygiene.check: false` for a lab it lacks; a doctor that cannot run (no `make`, no `doctor` target in the checkout, a timeout) is no reading and the project is admitted), the **boot grace** (kind `boot`, `domains/capacity/boot.ts`: while the host's uptime, from `kern.boottime`, is under 30 min,
  no new lead until the five newest minute samples, all taken since the boot, show a load under a quarter of the ceiling and the newest
  sample's memory is under 80 % in use, then at most one lead per 2 min; resumed leads count against the seats as always; the reason reads
  "host booted N min ago: …"; an unreadable uptime applies no grace and says so as a note), the host's 1-minute load (kind `load`; and the **throughput rule**, below), its memory (swapouts and swap against ceilings; the swapouts are the higher of the pass's own rate and the minute samples' last 300 s, `sustainedSwapoutMb`, so a lull between bursts does not open the gate; the memory that a
  lane's `memory` reserves for its running leads and the candidate counts as swap in use, `docs/plan.md` "Lanes"; then the
  learned fit (and, after the memory rules, the disk fit: kind `disk`, `domains/capacity/disk.ts`, "A binding cap and the disk fit" below): a repo with at least three sampled attempts is refused, kind `memory`, when its median lead (the median of its newest ten attempts' peaks) does not fit into
  the free memory of the newest host sample (not older than 5 min) less headroom (the larger of 2 GiB and 8 % of RAM) and less what the running leads are still expected to take (`leadGrowth`, `domains/capacity/leadcost.ts`: each claim that started under `RAMP_MS` (2 min) before the host sample the free figure comes from, or after it, whose repo has a learned size takes that size less what its newest sample holds, 0 when it has none, never below 0: an older lead is in the reading, and a lead holds the same within its first minute as ten minutes on (475 against 520 MiB over 239 leads, 2026-11-15), its peak being a burst that no age settles, which the headroom and the swap and pressure ceilings hold; a lead resumed from a wait is a new process and starts again; a lead admitted in the same pass has no sample and takes the whole figure, so one pass cannot admit several against one reading; a repo with no learned size keeps the lane's constant; the refusal says "N young leads still take X GiB more"); the running leads' test peaks are not reserved here, the slot grant holds them back (`SlotFit`); it
  replaces the lanes' `memory` for that repo's leads, never refuses with an unknown figure and never the only lead on the host).
  **What a lead is learned to take** (`learnLeadCost`, `domains/capacity/leadcost.ts`): an attempt's peak is its worktree's largest
  sample of the six hours before its last one, from the repo's relearn point on; the figure is the median (nearest rank) of the
  newest ten attempts' peaks, except that a falling cost is believed sooner than a rising one: when the newest three **settled**
  attempts (ended, no sample for 10 min, or run 30 min) all peak below that median, it is the largest of the three (the refusal
  says so). Too early is still caught by the swap and pressure ceilings and the slot grant; too late is idle seats with work
  queued. `factory capacity relearn --repo <name> [--at <time>]` (owner, orchestrator and a lead, whose `set_by` reads `agent`: an Issue's own ship step may set a point; `lead_relearn`, `migrations/1034_lead_relearn.sql`;
  default now, never in the future) ignores the repo's samples before the time: with fewer than three attempts after it the repo is
  on its lane's memory prior as a new repo is, and `factory queue order` carries a note per repo with a point (and the refusal
  says "learned from the attempts since …"). `read/lead-costs.ts` keeps the same window and point, with its plain p80, beside it (the burst a lead reaches, not the size the fit reserves). The
  candidate's lane (`lanes: {apple: 1}` in `project.yaml` caps the leads of a resource class inside the repo, a fix is
  never held; `domains/capacity/lanes.ts`), the repo's claims (`leads: N`, 64 when the project states none, which is no cap beyond the host (memory fit and load above, the accounts below), and at most 64, a larger value is clamped with a warning in `factory project show`; a repo states a smaller `leads` only for a shared resource the factory does not model (not its merge window, deploy queue or disk, which `factory merge-lock`, `deploy-lock` and the disk fit hold), with the reason in a comment beside it, and a cap that binds while seats idle is a finding (NL32, NL48); plus one for a fix; `pace` allows one), then an
  account with room. **Seats:** each account has its own cap (`FACTORY_ACCOUNT_LEADS`, `iu=20,me=10,me2=10`; an account not named takes `FACTORY_LEADS_PER_ACCOUNT`, at most 64; `factory capacity get` shows each account's `leads` beside its `cap`, and the `cap` refusal names every open account with its leads and cap). **Accounts are read in-process from `packages/accounts`, and the package alone decides (`adapters/planning/accounts-source.ts`):** the poll (once a minute) calls its `readStatus` (the registry, the cache files, the modes in force; no shell-out, no `FACTORY_CLAUDE_ACCOUNT_BIN`, no registry path of the factory's own: `CLAUDE_ACCOUNTS_REGISTRY` and the package's resolution) and stores, per account, the windows beside the package's verdict for the bulk lane: whether it takes work, its place in the order, why not and when it opens again (`capacity_readings`, `bulk_*`, `closed_why`, `opens_at`). The server keeps no window limit, weekly pace or room-left order of its own; `claude-account rank --lane bulk` and `factory capacity get` show the same order. The pick takes the open account with the lowest place, skipping accounts at their lead cap or loaded since their sample. An account the owner paused, drains or reserves is the package's business (`factory accounts mode <id> paused --until <iso>` writes the override through the package, so `claude-account mode` sees it; `factory accounts status` is `GET /v1/accounts`: the package's status with the seats taken and free and the leads running beside it). An account a lead's turn ended on a 401 for stays closed (`account_auth_marks`) until its login Errand closes. A reading the poll has not renewed for ten minutes admits nothing. An account is paced by sample (one new lead per quota sample) only when it has a 5-hour window above 70 %; an account with only a weekly limit, or a window below that, takes leads up to its cap in one pass. A lead that runs into the wall (`limit_stop`) stalls its Issue as `wall` and continues when the window resets: the wait is the reset of the window that closes the account, or, while the newest sample was taken before the wall and does not show it yet, the reset of the window nearest its ceiling when that window is within 10 points of it (the package's `wallResetAt`, stored on the reading, read by `windowOf`; a rate limit far from any window is a throttle and wakes the lead as before), so the steward neither wakes it early nor nudges it and `lead_idle` stays quiet (a stalled Issue is not a working lead). While the window is closed and another account is open with seat room (`pickAccount` over every account but the one it left), the steward moves the lead instead (`seats.move`, `moveWalled`): the attempt's assignment and its claim go to that account and the Issue is woken with the move in its detail. `noteLead` delivers that wake by ending the session and starting the same session again (`claude --resume`) under the new account's `CLAUDE_CONFIG_DIR`, the way a dormant lead is revived, and stores the account on the lead's row. Nothing is copied: the transcripts of every account lie in one `projects/` directory (the other accounts' `projects` is a symlink to the default one, `dotfiles/docs/claude-accounts.md`). The cost is one uncached read of the whole context, since the prompt cache is per account; it is only paid against a wait of hours. No other account with room: the lead waits for its window as before. **Seat raise:** when work is queued for the account cap and each of the newest five minute samples shows a load
  of at most a quarter of the ceiling and swap below its ceiling, the pass raises every account's cap by the leads that fit into the
  free memory (`domains/capacity/seats.ts`, at most `FACTORY_SEATS_MAX_BONUS`, default 2, 0 is off); never the repo's `leads: N`, never
  past an account's window, and the `cap` reason says `(raised by N: the host is idle)`. **The throughput rule** (`DEFAULT_LOAD_PER_CORE`, `DEFAULT_PROCESS_CAP` in `domains/capacity/host.ts`; `hostRule` in `app/planning-settings.ts`): the load ceiling in multiples of the cores (`FACTORY_LOAD_PER_CORE`, default 3, so 36 on 12 cores) and a cap on the host's process count (`FACTORY_PROCESS_CAP`, default 1800, from the newest minute sample's `processes`, not older than 3 min; an unread count applies no cap), because the panic class is a process storm, not memory; an over-cap host is refused with kind `load` and "N processes (cap M)". Both limits are always on, with no setting that turns them off (the Console's load ceiling is the one in force). `factory.admission_shadow` (`migrations/1024_admission_shadow.sql`) is no longer written; dropping it is a later row. An env file that still sets `FACTORY_LOAD_RULE`, `FACTORY_SLOT_AIM` or `FACTORY_LOAD_CEILING` starts: `scripts/env-file.sh` drops the line with a warning for one release. The first that says no names itself and its numbers as the queue reason. It never spills to another
  account past a window or a cap; with every account closed it waits for the first opening. Owed Issues are served
  before new ones, in the repo and on the account: a woken lead is the same session on the account it was admitted on, so the
  account cap never refuses its resume (only the repo's claims and its lane do), and from the moment its wait ends it counts in
  its account's leads, so a new lead cannot take the seat it will run on. A lead in a wait that gave its claim up is idle and
  counts nowhere. A herd woken at once (a red master closing and waking a dozen deferred leads) takes the repo's places in
  order of its waits, oldest first, up to `leads: N`; the steward counts a refusal for a claim as a stall only when a claim
  would be granted to that lead now, and names the account it resumes on. The gates (lead cap, loaded) stay the factory's; whether an account is open and the order of the open ones come from the package, read in the same poll as the windows.
- **A turn that ends on an API error** (`domains/leads/apierror.ts`, `app/leads-api-errors.ts`, a step of the leads tick). Claude Code
  fires `StopFailure`, never `Stop`, when a turn ends on an API error (hooks reference, "StopFailure": `error`, `error_details`,
  `last_assistant_message`), so the session looks mid-turn to anything that waits for a `Stop`. The hook (every `error` type now,
  no matcher) spools it as `api_error` (a `rate_limit` stays the `limit_stop` wall); a session whose hook did not run is found
  by its transcript: a turn open and silent for `FACTORY_API_DETECT_MS` has the end of its transcript read (`TranscriptTails`,
  the last `assistant`/`user` record with `isApiErrorMessage`, its `error` and `apiErrorStatus`) at most every
  `FACTORY_API_PROBE_MS`, and the same fact is stored. `deriveSession` reads an `api_error` as the end of the turn
  (`SessionView.apiIncident`: the errors since the last clean `turn_ended`), so a note waiting for the turn to end is delivered.
  A prompt the account's closed window refuses (a resumed lead's first message) fires `UserPromptSubmit` and nothing after it: a
  turn open and silent for two minutes, with no process in the lead's tree, on an account capacity reads as closed (the table is read fresh, and does not depend on quiescing) is stored as
  the `limit_stop` the hook missed (`app/leads-held.ts`), so the Issue stalls as a `wall` and is woken or moved like any other.
  `kindOfApiError` reads the fields before the words: a 401 or an expired or revoked token is **auth**; a 429, 5xx, a
  timeout or reset, `server_error` (also mid-response, which adds "your last response may be cut off, re-check what you did" to
  the note) and a 403 typed `authentication_failed` (a Cloudflare challenge: 10 of 10 on 2026-11-13, none needed a login, though
  Claude Code prints "Please run /login") are **transient**; anything else is left to the steward. Transient: one `continue`
  (a `resume` delivery, key `resume:<session>:<incident>:<n>`) after 1 minute, then 3, 10, 10, 10, five at most per incident; three
  or more leads failing within five minutes are one **edge incident**: one clock, one `continue` per `FACTORY_API_STAGGER_MS`
  (30 s) among them, and one `api_edge_incidents` row (leads, window, and the owner's `plan-*` sessions in the same state,
  counted and never resumed) that the friction read shows as `api_transient` (informational, never a finding). Auth: the
  account gets an `account_auth_marks` row that capacity reads as "not signed in" (no admissions on it, nothing moved), and
  one Errand "log in account X" (request key `account-login:<account>`, no check: the picker still says the login is fine); its

  seconds over their run, `learnedCores`; `DEFAULT_STEP_CORES` 1 with none), and a step beyond the base waits (`cores`) while
  the running steps' learned cores plus its own exceed the host's cores, so light steps run beside a heavy one; `factory slot
  run` reports the exit's resource usage, which counts every reaped descendant (the `ps` samples alone missed short-lived
  workers: 0.4 cores for a step whose host minutes said more). *Host-wide classes* (`stepClassOf` in `domains/capacity/slots.ts`):
  a step named `<repo>-apple` or `<project> apple` (the Apple slot's name in dotfiles `docs/apple-signing.md`) is of class
  `apple`, and one step of a class holds a slot at a time whichever repo runs it (`class`); a waiter held by its class is
  passed and never holds the line. Cargo builds are no class: the fit packs them. *The line's order* (`lineOrder`): a waiter's
  place is when it asked plus its learned run (median of its 8 newest), so a short step passes a long one that asked a little
  earlier; the place is fixed when it asks, which is the ageing. *The test line steers the lead admission* (`lineRefusal` in
  `domains/capacity/admission.ts`, kind `tests`): no new lead while more steps wait for a slot than run and half of them have
  waited longer than a step takes (the median run of the last day's `step_costs`); a fix is never held. Replayed over the 30
  hours to 2026-11-16 21:50 UTC it would have held admission 404 of 1781 minutes. The lead admission's `load` gate is the
  tripwire too, not the instant reading. `factory capacity` still shows the configured `FACTORY_SLOTS` and `FACTORY_SLOTS_MAX`; the aimed count and mode are
  in `slotAim` of `factory read capacity-loop`. Steps run at normal priority: a test of
  `taskpolicy -b` and its neighbours is in `docs/research/2026-11-14-taskpolicy-steps.md`.

### Steps off the mini

Issue 1793, the Spec "Steps that run off the mini" (rev 3) and the planning session's measurements of 2026-11-17. A
repo names its steps in `project.yaml` `steps:` (`docs/project.md`): the Makefile target, what each `needs`, and
`remote: true` when it passes on Ubuntu 24.04 in the step image. No host is named in a repo's file: the step host is the
owner's setting, `FACTORY_STEP_REMOTE_TARGET` (an ssh alias; unset, every step runs on the mini) and
`FACTORY_STEP_REMOTE_PROJECTS` (the projects admitted to it). One line, two hosts:

- **Placement** (`app/capacity-slots.ts` `touchSlot`, `domains/capacity/remote.ts`). The mini's rule is as before over the
  rows that are not the VPS's (`capacity_slots.host`). When it makes a caller wait, the caller can run off the mini (the
  CLI sends `remote`), its project is admitted, its step is declared `remote: true` and needs nothing only the mini has
  (`mac`, `apple`, `secrets`, `services`; a step of the host-wide class `apple` never, whatever a file says), the VPS gets
  it when `decideRemote` finds room and `finishesSooner` holds. Room: a probe at most 90 s old, production's own pressure
  stall (`system.slice` memory and io `some avg10`) not over the pressure line (below), the disk under the 85 % its alert pages on with a new copy
  counted, the step's peak beside the running steps' peaks and the mini's headroom rule in `MemAvailable`, its cores in the
  idle ones. Sooner: its learned VPS run (unknown: 1.7 times the mini's, as measured) against the expected mini wait (the
  holder that frees its slot) plus its mini run. There is no fixed share of the VPS.
- **The pressure line** (`kernel/remote-pressure.ts`). Each probe reading is stored once (`remote_samples`: memory and io
  pressure, and how many step containers ran). The samples taken with none running over the last 3 days are the baseline;
  with a day of them (at least 24 h between the first and the newest, 200 samples) the line is just above each pressure's
  p99 (the larger of half a point and a quarter of the p99 on top, at most 10 %), else 1 %. At rest the VPS reads 0.00, so
  a flat 10 % meant production already stalled a tenth of the time. The line is derived from the samples at each read, so
  the baseline sits beside it in Throughput's "Steps by host" (`tests.remote.pressure`).
- **Why a step ran where it did** (`step_placements`, one row at each grant of a step its project declared remote): on the
  VPS, or on the mini because a slot was free (`free`), the VPS had no room (`no_room`), would not finish it sooner
  (`not_sooner`) or the step was held (`held`). The reason is the VPS's last refusal while the step waited, kept in the
  process; a restart reads `free`. Throughput lists each such step with its runs per host and these counts.
- **The probe** (`adapters/remote/probe.ts`): one `ssh` of at most every 30 s, started by a placement read and never awaited
  by it. It reads cores, load, memory, disk, the PSI and the step containers, and removes a step container whose slot is
  gone (older than 2 min, the CLI killed with its session up).
- **The run** (`apps/cli/src/remote-step.ts`). The worktree travels as a git snapshot: a copy of the index, `git add -A`,
  the `carry` paths forced in, `commit-tree` on HEAD (the worktree and its index untouched); pushed to the project's bare
  repository on the host (`factory-steps/<project>.git`, with `origin/<default>` so a step that diffs can), checked out in the
  slot's worktree (`factory-steps/<project>/<n>`), 0.4 to 1.4 s on a warm copy. The image is the repo's `dockerfile` or the
  factory's (Ubuntu 24.04, git, jq, make, shellcheck, the bun of `packageManager` and the PostgreSQL 16 server binaries: `initdb`, `pg_ctl` and
  `postgres` on `PATH`, `PG_BIN_DIR` set, issue 2114), built once per content and per image revision (`factory-step:bun-<bun>-r<n>`,
  `IMAGE_REVISION` in `remote-step.ts`, bumped when the image changes without its bun). A step starts and stops a private cluster in
  its own container (loopback and a unix socket need no network, a non-root uid needs a passwd entry: the image's `ubuntu` is uid
  1000, the step host user's); there is no `needs` word for it, because every factory-image step has it and a repo's own
  `dockerfile` carries what it needs itself. The install runs in a container
  with the network, the step in one with none (`needs: [network]` keeps it), both under `--cgroup-parent
  factory-steps.slice`, `--cpu-shares 2`, `--oom-score-adj 1000`, a memory ceiling of 1.5 times the learned peak (at least
  1 GiB), `--cap-drop ALL`, `no-new-privileges`, the host user's uid, mounted at the caller's own path; the step gets
  `FACTORY_STEP_CORES` (the idle cores at the grant) and `FACTORY_STEP_MEM_MIB`. Production wins by priority, not a
  partition. A whole no-op step costs 1.9 s.
- **Retention** (`adapters/remote/trim.ts`, issue 2035; measured 2026-11-17: `factory-steps` 7.2 GB, slot worktrees 1.6 GB
  each with `node_modules`, the bun cache 1.9 GB with no bound). The probe starts one ssh of a shell script at most every
  6 h (`TRIM_EVERY_MS`), apart from its own call, after a probe that saw no step container; the script itself does nothing
  while one runs or docker does not answer. It removes a slot copy (`<project>/<n>` and `<n>.run`) whose `.run`
  directory, rewritten by every step of the slot, is older than 7 days (`COPY_IDLE_DAYS`), prunes the bare repository's
  worktree record and keeps the bare repository; and a whole bun cache entry no install read for 14 days
  (`CACHE_IDLE_DAYS`, by access time: the mount is `relatime`), tightening to 7, 3 and 1 day while the cache is over 3 GiB
  (`CACHE_CAP_GIB`). A removed copy costs the slot's next step one checkout and install, a removed entry one download.
  A step that starts mid-trim and meets a removed copy fails as a host failure and runs on the mini. The server logs a
  line when something was removed (`steps: trim: removed ...`). The step images carry `factory.image=step` (set at build;
  an image built before it has none), so the host's daily `docker image prune` can keep them with
  `--filter label!=factory.image`; that prune is the vps repo's.
- **Results.** The exit code is the step's own. ssh's 255 and docker's or the setup's 125 to 127 are the host's failure:
  the caller goes back to the mini's line at its old place (`notOn`). A red on the VPS is not yet a red: the same call runs
  the step again on the mini, and only that result reaches the caller; a green there is stored `disagreed` with what the red
  run failed on (`step_costs.disagreement`: the failing test names from its JUnit with their remote duration and the
  timeout its output names, else the last 40 lines of the output). `step_costs.host`, `tree` (the snapshot's tree) and
  `disagreed` record it; the run time is learned per host, the peak and cores across hosts. The VPS's holders and pinned
  waiters are not the mini's test line for the admission. Throughput's "Steps by host" reads them.
- **The hold** (`kernel/remote-hold.ts`, derived from the ledger, never stored). A disagreement holds the step on the mini
  for 1 hour; each further one within a week of the hold's end doubles it, up to 7 days; the first green run on the VPS
  after a hold halves it (once; below an hour it is gone). The wait line says `it stays on the mini for 2 h, until <time>`,
  and Throughput shows the hold with its end. A test name that disagrees a second time files one signal to its project
  (`recordStepCost`: the test, its remote duration, the timeout), so the repo fixes the test instead of the factory losing
  the host.
- `FACTORY_SLOT_HOST=mini|vps` pins one call (a step that needs what only the mini has is never pinned off it);
  `FACTORY_SLOT_REMOTE=0` keeps one call on the mini.

Not built: proving runs in the host's idle time (a step earns its place before it is used), pausing step containers when
production stalls, a result cache keyed by the tree, a browser in the factory's image, a third host.

## Quality

- **Ship** (`app/quality-ship.ts`, `domains/quality/gate.ts`): the lead names merged commits, or none: then the factory
  finds what the Issue's branches landed (`Commits.landed`: each attempt's branch, newest first; by content: the first
  default-branch commit that holds every file the branch changed since it forked as the branch has it, a squash or a
  rebase; or, for a branch the default branch holds and the lead made a commit on, the first-parent commit that brought
  it in, a merge or its tip). Either way git must find them on the default branch and
  newer than the Issue's cut (its first attempt's, so a later attempt ships what an earlier one landed), read by the
  factory, never taken from the lead. Without that the ship is refused with the error named and
  counted as friction; so is the ship of an Issue flagged `checkpoint: spec` with no Spec submitted ("The Spec checkpoint", under Checkpoints). A review is recorded as evidence when agw's ledger covers the range, and its absence is recorded
  with its reason; it never refuses a ship (NL23). A commit agw routes to light is no absence (NL12: a review is owed at standard or deep), so a range whose only uncovered commits are light is recorded `not_required` and the friction loop does not count it; the brief has the lead read `agw review covered` before the merge. Whether a rebased, squash-merged change still counts as reviewed is
  agw's judgment (`covered`), not the factory's; `factory issue ship` prints one stderr line naming the range to `/review`
  when the answer is `uncovered`, or the reason when it was not read. The lead also states one line per acceptance line of the Issue
  (`--acceptance "met: ..."` or `"not met: ..."`; the factory parses no criteria), recorded as `acceptance` evidence and shown on the
  Issue page; the natural forms are normalised (a list marker, `AC2:`, bold, a dash for the colon), a line over 500 characters is cut, and a malformed line is refused (422) with the corrected `--acceptance` line built from what was sent; a `not met` never refuses, and a ship that states nothing is counted as
  friction (`unstated_acceptance`) like an unreviewed one. The pull request the commits landed through is read from GitHub
  (`adapters/quality/ci.ts`, the `Ci` port) and its head's CI recorded as `ci` evidence (`green`, `red`, `running`, `missing`
  when no pull request or no check was found, `unknown` when GitHub could not be read); it never refuses a ship, and a red
  or missing one is counted as friction (`unproven_ci`). One refusal reads CI at the ship (NL42): after a Watch regressed on the default
  branch's CI, a ship is refused while that CI is still red for the commit it lands at (`ciStillRed`, `quality-ship.ts`). A second refusal holds a repeat ship after an alert regression: while the Issue's alert is still down, a ship naming no commit the last accepted one did not is refused (`afterAlertRegression`, `alertStillDown`, `quality-ship.ts`; the alert state is `intake.subjectsOfIssue`, wired in `main.ts`). A third refusal reads the deployed version (NL49): under deploy mode `make`, a change that deploys is refused while `make version` names a commit that does not hold the landed one (`notDeployed`, `quality-ship.ts`; the check is the Watch's own, `Proof.run` with the version only). A project that ships by push (no `via: pr` rule) or has no
  `project.yaml` records no `ci` evidence and asks GitHub nothing. `evidence.ts` decides whether the paths deploy at all; its built-in inert
  paths equal `scripts/verify.sh`'s. A project's `deploy.paths` (globs in `project.yaml`; empty by default, which changes nothing) narrows
  that further: with some declared, a path deploys only if a glob names it and it is not built-in inert, so a rewrite built beside the
  running system ships with `deploys: false` (no deploy, no version check). The gate, the watch's version check (`deployedHolds`) and
  `ProjectChecks.deployPaths` all read it; `scripts/verify.sh` stays the built-in floor.
- **Watch and verify** (`domains/quality/watch.ts`, `app/quality-watch.ts`): the project's `make verify` and probes run on
  their own loop, so a slow verify never holds the leads' pass. What the watch runs is the synced `project.yaml`
  (`app/quality-projects.ts`): deploy mode, `hold` as the window, `make verify` from a target, URL targets and probes. Only
  mode `make` reads `make version`; a missing version target there is red. A file with no target leaves verify to the
  Makefile, and a repo without a `project.yaml` is read from its Makefile alone (`adapters/quality/projects.ts`). A red check is retried with a doubling delay before it is
  a regression, unless it is a `make` target that failed the same way in the repo's last finished run before the ship, another Issue's watch, or in the last run of another Issue's watch of the repo that regressed in the last day and no pass of that Issue has answered (one red, one owner: that lead has it; the Issue's own regressions never count) (every failing line of this run, numbers aside, is among the failing lines of those runs together, so a drift list that shrank or a changed number is the same red, a line none of them had (an added drift item too) is not; the Regressed note opens with the failed checks' names and first failing lines): that one is stored `inherited`, counts green, is never retried and stays on the Issue's page; a regression returns the Issue to its lead, twice, then it stalls. A checkout that cannot be read is
  rechecked, never passed. In a project that ships through a pull request (`ship:` `via: pr`) verify also reads the default
  branch's CI for the exact merged commit (`ci` check; `mergedSha`, the first-parent commit that holds the ship's named commits, never the branch tip at the ship, which a later commit of another lead may have moved): green passes, red is red (unless the first parent of the merged commit, the default branch before the change, was red on the same first failing check: that red is stored `inherited`, counts green and is no regression of the Issue; a parent that is green, running, missing or unreadable leaves it the change's), and a run still running (or not yet visible
  within 10 min of the merge) is neither, so the watch is looked at again after `FACTORY_VERIFY_RECHECK_MS` and does not pass;
  one running past an hour is red, and no run at all after 10 min passes with that said (the repo may have none). A pending
  CI wins over a red `make verify` until it settles (`outcomeOf`: blocked first).

## Checkpoints

A Decision is a form with every field required (recommendation, what was checked, cost per option, what happens with no
answer). It is settled in order: the Judge (`factory-ask`),
which reads the plan, the docs and the precedents: the owner's own earlier answers, never the Judge's, a default's or the orchestrator's), the default after its wait when the option is reversible, then
the owner. A step is a claimed call with a 35-minute lease: a takeover point, not a limit on the call, since a retaken call carries the same idempotency key and agw joins the run it started. A form with a missing
field is refused (422 `missing_field`, the fields named, nothing stored). The Judge sees every Decision before the owner
does: a failed Judge call is tried again after a 5-minute backoff, three tries in all (`decision_steps.tries`), and while
tries are left the Decision is not the owner's (no owner step, no page, not in Needs). A Decision with a default still running down its wait has no owner step and no page either, but it is in Needs from the moment the Judge is done with it (passed it on, rejected its answer, or failed for the last time; `read/needs.ts`: the Issue waits on the owner, who may answer before the default is taken). After the third failure it reaches
him with the failure in the Judge step's detail; `passed` and `rejected` stay final. The Judge's step is on the
`DecisionView` (`judge`) and its reason on the Needs item. A second ask from the same asker while the Issue still waits on
its open Decision amends that Decision: the form is replaced, the new rendering is the artifact's next revision (note
`amended`), the steps and unsent pages are cleared so it is settled afresh, and a verdict of a call that was out during
the amend is dropped (the form digest taken at claim no longer matches). The same form again is a replay; an answered or
withdrawn Decision is never amended. An Errand names what the lead tried (`tried`, a gate: not stored) and is refused at the raise, nothing raised
and the route named, when it asks for what the host does (`refuseHostClass`: a door token or route, an install, a sudo step with no
no-sudo attempt shown, a Report missing from Needs you); `call` on an ask or an Errand makes a repeat one event. A lead that went on with the default it named settles its own Decision with `factory decision take-default` (`takeDefault` in `app/checkpoints.ts`: the lead's own Decision of the attempt there is, one that names a default; `answerIn` records it as `default`, `the lead took the default`), so the wait ends and a ship is taken at once instead of after the default's wait. the asker as the repo). A turn-away closes it `turned_away` with the reason as its note (there is no lead to tell); a pass puts it
in Needs without a page. Why not an Issue that holds it: an Issue per request files work no lead can do,
`errand_done` would wake it, and the work table has no "waiting on an Errand, no lead" cell. It carries `source`, `command`, `host`
(`macbook|iphone|portal|any`, from the asker or read from the words, `kernel/hands.ts`), `check_command`, `expires_at` (7 days
when it has no check and none was given; `never` and a check keep it) and `request_key`: a new request with the key of an open
one closes it as `superseded` in the same transaction (the same words again are a replay; asked again after it closed is a new
Errand). `closed_kind` and `closed_by` say how any Errand ended (`done`, `not_needed`, `expired`, `superseded`, `turned_away`;
by `owner`, `orchestrator`, `check`, `judge`, `loop`, `request`); the owner closes one as `not_needed` with `outcome` on `POST /v1/errands/:id/done`
(the Console's existing verb, no ninth one), and a lead's Errand closed that way tells its lead so. The `check` is a shell command
the server runs, so only the callers that can run a shell may set one (`api/policy.ts`); it runs through `sh -c` in its own process
group, 30 s, the server's secrets left out of its environment (`adapters/shell/check-runner.ts`); wherever the factory quotes output it
keeps the first 20 lines and the last 20 (`kernel/run.ts`), because the reason is at the top.
**A done is not always done** (`finishErrand`, `POST /v1/errands/:id/done`). A result that says the pushed run failed (`run.status`
`failed`, `timeout` or `running`, or a non-zero `run.exit`; the words `ask-human.sh` wrote before it sent `run`, `ran on the MacBook
and failed (exit N)`, count too) leaves the Errand open and records the run (`run_*` columns: tries, status, exit, head, tail); Needs
shows `tried, failed: <first error line>` (`tried`) and the Console its output. A done on an Errand with a `check` runs the check at
once, outside any transaction: exit 0 reopens it with `check_note` `marked done but the check says still needed` (the hourly pass
keeps that note), exit 1..125 closes it with the check's output in the note, a check that could not answer closes it as before. A pushed run that exited 0 (`run.status` `done`, or the words `answered on the MacBook (exit 0)`) with a check that still exits 0 is stored as `run_status` `done`, which `run_attempts` does not count; the desk pass never pushes that Errand again, and turns it back to its lead once, with the check's output, when the check it runs in that pass still exits 0.
**What an Errand needs** (`errands.need`: `secret`, `hands`, `approval`, `place`; `domains/checkpoints/need.ts`). Set when the screen
lets it through and shown on Needs you; an Errand that was open before the column existed gets it from `assignNeeds` in the
`settle` pass. The rule over the Errand's shape decides first, and the screen model (`ErrandScreenAnswer.need`, optional, never
`approval`) only the rest, `hands` by default. A secret word (1Password, a biometric, sudo, the secrets reseal) is `secret`.
A command addressed to the mini (`ssh <alias> '...'`) or the deploy gate's release (`deploy-release`, `gate.py release`) that names
no secret is `approval`, and with a command it reaches the owner by rule (`screenByNeed`), no model asked. Another command for the
MacBook with no physical step is `place`; a device, hardware, a portal or a visual check is `hands`. The desk pass pushes a MacBook
dialog (`pushQueue`) only for `secret` and `hands`: a `place` waits on Needs you with its command to copy (his "Push what waits"
button still pushes it), an `approval` never goes to the MacBook.
**Decided by rule before the owner** (issue 1714, `domains/checkpoints/triage.ts`, replayed by `scripts/errand-replay.ts`): a request or a lead's Errand is read by its shape
before it can reach him, and a secret, sudo, passphrase or hands Errand can only get `reach`. (a) A command that runs wholly on the mini or
over keyless ssh (an ssh to the mini or a server, `hc ... --on mini`) with no secret word, no physical word and none of his yes (a restart or
power-off, `hc server`/`hc update`, the gate's release, a recursive delete, a service boot-out) is refused at the raise
(`refuseKeyless`: the lead is on the mini, so it runs the command itself); an `approval` is now only a yes of his. (c) A request (no Issue) that
asks him to pass a bot check (`refuseBotCheck`) is refused: the run reports the page as blocked and goes on with other sources; an Issue that
cannot be answered without the page raises an Errand of its own. (d) The same need (`matchKey`) that the owner or the orchestrator turned back
within `DECLINE_HOLD_MS` (3 days) is refused with the turn-back note as the refusal text (`declinedMatch`; no new column). (e) A lead's
Errand states its need (`--need secret|hands|place`, `ErrandBody.need`; `place` needs `--cmd`), else it is refused with the field named; a request
with no command whose words name no secret and no physical step must state one too. A stated need never lowers the rules' need: it is
checked for presence, not stored. (f) `refuseOffMacbook`: a command for the MacBook (or with no host) whose head word, in any segment outside quotes, is a mini-only CLI (`factory`, `secrets-run`; `MINI_ONLY_COMMANDS`) is refused at the raise, before any page or dialog, because the dialog would fail with exit 127 and leave a second Errand; a best-effort read of the shell line, and a word joins the list on evidence. (b) `verbFor`: a MacBook command that is exactly a fixed class and names no secret or physical step is run by
the screen (`screenErrand`, before the other looks, only when `SettleDeps.macbook` is set) through the gate's fixed verbs

`dotfiles-sync`; `adapters/shell/ask-human.ts` `askHumanVerbs`, no transaction open) with no dialog: exit 0 closes the Errand `done` by `loop`
(`finishRan`), the Issue and every joined Issue hear `errand_done` with `ran` (the verb and its output) and nothing is paged; any other exit (126 the
gate lacks the verb, 255 unreachable, git refused) reaches him as a `place` Errand with the reason in its screen note. The MacBook side of the verbs
(`report`'s registry, `repo-pull`) is dotfiles': the contract is the signal filed with this change. The KPI `errands_reached_per_100` is the Errands
that reached him per 100 Issues filed; its parts are the shares needing a secret or hands, a secret, hands, a place, or only his yes.
**The one place the factory ran itself before 1714** (`app/checkpoints-sync.ts`, `isSyncCommand`): a `place` Errand whose command is exactly
`git -C ~/SourceRoot/dotfiles pull --ff-only`, optionally followed by `make herdr-app-setup`, is run through the MacBook's

stays on Needs you with its command and the loop names the exit. It records no failed run, so a dirty MacBook tree never retires
the Errand. Any other place command is the owner's.
**Auto-run** (dotfiles Issue 2393, this repo's Issue 2388). `ask-human.sh push` sends a command to the MacBook gate's `auto-run` verb before it opens a dialog: a command that is byte-equal to a catalogue class the owner granted once (a local consent file the mini cannot write) runs with no click, with the screen unlocked where the class needs the 1Password prompt; 77 (no class, not granted, kill switch) falls back to the dialog, 75 (locked screen, biometric class) leaves the request pending for the next pass. Not built: a Needs-you label for what an Errand waits on; any Errand still open is one the gate declined, and the owner's consent (`consent grant|revoke|list|off|on` of the MacBook's `human-queue.sh`) is MacBook-side only.
**Approve** (`POST /v1/errands/:id/approve`, `factory errand approve <id>`, the Console's button; owner only, the orchestrator is
refused). On an `approval` Errand that reached him, the server runs the command on the mini (`app/checkpoints-approve.ts`:
`ssh <alias> '<x>'` is run as `<x>` here, the server's secrets left out, a 30-minute hang guard), answers at once, and records what it
came to as a pushed run: exit 0 goes through his done (`finishErrand`, so the Errand's check decides, and the lead hears it),
a failure leaves it open with the first and last lines. **What this guards and what it does not.** The route is owner-only, so a
lead's agent token and the orchestrator's are refused. An agent on the mini is not kept from the owner token, though: with
`FACTORY_TOKEN` empty the CLI resolves it through `secrets-run` (`credentials.ts`; a set token always wins, and an interactive
`claude` session on the mini starts with the orchestrator token set, so its CLI never reaches the resolver unless it writes
`FACTORY_TOKEN= factory …`), and the Console listener has no per-request identity. So Approve is a recorded consent of the
same strength as a Decision's answer, not a barrier, and it
gives an agent nothing it lacks: the command runs as the user the agent already is. What the MacBook dialog had that Approve does
not is a click on another machine; the Decision on this Issue (decision_01a1d9e5) put that trade to the owner, and reverting is one
condition in `pushQueue` plus the route.
**Repeats join.** A lead's Errand, or a request, that is the same need as an open Errand does not raise another. The same need is
the same exact command or check, or the same `match_key` (`domains/checkpoints/match.ts`, stored when it is raised): the lead's
own `needKey` in the repo (`--body '{"needKey":"census-ua-contact",...}'`), else the command with its whitespace and a trailing
`;` normalised (the same wherever it is raised), else the one-line summary lowercased and stripped of punctuation, in the same
repo (a request's repo is its asker). Errands raised before the column existed carry none and join by exact command or check
only. The Issue waits on the open one (`errand_raised` with its id, a row in `errand_joins`), the owner is paged once, and the Errand's
end (`errand_done`, a turn-back, a check that closes it, a retire) is written to every joined Issue in the same transaction
(`eachJoined`); Needs you names the joined Issues on the Errand (`joinedIssues`, "also awaited by Issues 1333 and 1335"). A request under a key that an open one holds replaces it as before, and joins only when its command is the same.
**A command that fails twice ends** (`MAX_RUN_TRIES`, `retireFailed`): a pushed or approved run that came back unsuccessful the
second time is not offered a third time. The Errand closes `turned_back` by `loop`; its lead (and every joined lead) hears
`errand_done` with `turnedAway` saying the command failed twice and must be corrected, a request's asker reads the same words as
its note. **Checks run with `/usr/sbin` and `/sbin` on the PATH** (`checkPath`: the server's launchd PATH has neither), and a
check whose output says a command was not found, or that exits 127, is `broken` (`checkVerdict`): never "still needed", noted
as `the check is broken: ...` on Needs you and put once on the lead's record (`tellCheckBroken`: a `noted` event a waiting lead reads at its next turn), and the owner's done closes the Errand.
A failed or refused call is tried again after the Judge's 5-minute backoff, three tries in all (`errands.screen_tries`);
after the third the Errand reaches the owner unscreened (`screen_by` `failed`).

**The recheck.** A Decision or Errand that has been in front of the owner longer than `FACTORY_CHECKPOINT_RECHECK_MS`
(6 h; 0 is off) is looked at once more, by `recheckOpen` (`app/checkpoints-recheck.ts`), which the `settle` loop and
`checkpoint pass` run before the settle steps and the screen, so the second look owns the reason for anything past the
threshold. A Decision is at the owner when its `owner` step is `open`, an Errand when `reached_owner_at` is set. It is
due when the threshold has passed since it reached him or was last looked at, and the Issue has an applied event beyond
the version the last look saw (for the first look, the version when it reached him, read from the log's times), so
nothing is checked twice without news. Deterministic first: an Issue that is closed, or no longer waits for it, withdraws
the Decision or finishes the Errand with the reason (`withdrawalReason`, which also names a newer Decision on the same
question; a checkpoint the Issue still waits for is never withdrawn). Otherwise the Judge looks again with the Issue's
events since it was raised (`factory-ask` for a Decision, `factory-errand` for an Errand): an `answer` that passes
`guardVerdict`, or a turn-away, settles it through the usual paths (`answerIn` and its note, `turnAway`), so the lead
hears it and the owner can overrule it with a note. The events travel inside fields the workflows already read, because an
unknown field is dropped: appended to `checked` for the Judge, to `detail` for the screen, scrubbed, as data. Every look
is a row in `checkpoint_rechecks` (`outcome` `withdrawn`, `settled` or `kept`; `by` `factory` or `judge`; `reason`;
`through_version`; at most one per checkpoint and version) and one `rechecked` change on the stream (kind `decision`, `errand` or `artifact`, detail the id and the outcome), which the "Since you were here" band reads. A failed call is recorded as
`kept`, so a dead Judge is not asked again every tick. Call keys: `factory-ask:recheck:<decision>:<version>` and
`factory-errand:recheck:<errand>:<version>`.

**The Spec checkpoint** (issue 725). The owner wants few asks and the essential ones: an architecture or look-and-feel choice that
later Issues build on, a new public surface, a data model or migration of meaning, a dependency of weight, a UI screen he has
not seen. Those are a one-page Spec, never a Decision (order 2 and 3 of the standing orders, `domains/leads/brief.ts`; the
brief test pins the wording). Three parts:

- *The flag.* `checkpoint: spec` on a plan row, `factory issue new --checkpoint spec` or the `filed` event (`filed.checkpoint`,
  kept on the Issue as `checkpoint`; old events carry none). The filer sets it, and so may triage: a settle answer's optional
  `checkpoint: spec` (new public surface, data model, dependency of weight, unseen screen) rides the `settled` event
  (`settled.checkpoint`) onto the Issue, for any Issue triage was asked about but an incident. The triage pass counts them as
  `flagged`; Improve's specs per 100 Issues is the measure. The workflow side (agent-workflows `factory-triage`) must learn the
  field; until it does the answer carries none and nothing is flagged. The brief of a flagged Issue carries a "Checkpoint"
  section.
- *The gate.* `shipIssue` refuses a flagged Issue's ship until a Spec exists for it (any attempt; a Concept does not count),
  before any git read, as a refused ship on the record (so `refusals` counts it) with `SPEC_OWED` as the verb's error.
- *The owner gate* (issue 2157). `checkpoint: gate` (a filer's flag, never triage's; `filed.checkpoint`, `ReadIssueCard.gate`) owes the same Spec and refuses the ship alike, but only the owner's own verdict ends its wait: `staleReviews` leaves an open gate's review out (a closed one is still withdrawn), `screenSpecByRule` passes its Spec to him whatever its origin, the brief says so, and the Needs you card and the Issue header name it. What is `after` it stays blocked until the lead closes it from his verdict, and a verdict by the factory never ends it. A `settled` event cannot turn a gate into a plain `spec`.
- *Who gave a verdict.* `factory.verdicts.by` (`owner`|`factory`|`orchestrator`, migrations `1051_verdict_by.sql`, backfilled from the factory's own events, rechecks and screen settles, and `1059_verdict_by_orchestrator.sql`) is on `VerdictView.by` and `ReadArtifactLine.verdictBy`; the Console shows "By the factory" or "By your delegate" on a verdict the owner did not give. The KPIs still tell the owner's own verdicts from the factory's by the event's actor, and leave the delegate's out (`ownerVerdict` reads `by`). The delegate (issue 2541): the orchestrator may give a Spec's verdict (not a Concept's, a Report's or a gate's: `delegateRefusal`), recorded as `orchestrator`; the owner's own verdict on that revision replaces it (`replaceDelegatedVerdict`), clears its needed mark and tells the lead of an open Issue.
- *The timeout.* A Concept or Spec the owner has not answered for 24 hours is looked at once per revision by
  `recheckReviews` (`app/checkpoints-reviews.ts`, run by `settle` and `checkpoint pass` after `recheckOpen`; no model, no port):
  its Issue closed or no longer waiting: withdrawn (verdict `no_longer_applies` by the factory, pages cancelled); anything
  else, Concept or Spec, flagged Issue or not: **defaulted** (verdict `looks_good` by the factory with a note, `verdict_given`
  and `noted` by actor `factory`, so the lead hears "no verdict, go on with your defaults" once and the owner can still
  overrule with a note). Nothing stays in Needs you past the wait: there is no second push, because it would fall on the same
  hour as the default. A Report never waits on the owner. Each look is a `checkpoint_rechecks` row of kind `artifact`
  (`through_version` is the revision seen, so a revision is looked at once). `SPEC_WAIT_HOURS` (contract, `lane.ts`) is the
  one number; the brief and the gate's message quote it.
- *A Decision is a choice.* `askDecision` refuses a lead's Decision whose recommendation or default is to keep waiting
  (`refuseNoOpDefault`, `domains/checkpoints/decision.ts`: "Keep waiting", "Wait for review", "Do nothing", "Hold") with
  422 `invalid_request` naming `factory errand raise`: what it waits for is a person's chore (approve a PR, rotate a key,
  click in a UI), and a chore is an Errand. The steward's asks are exempt: a hold is a real answer to a stall. Order 2 of the
  brief says the same.
- *Taste.* The owner's verdict notes and annotations are the one signal of what he likes. `factory retro` carries them as
  `taste` (`read/retro-taste.ts`: his own verdicts with a note or a `with_notes`/`changes`, never the factory's defaults, and
  his annotations, each with artifact, repo and Issue; words dropped for the read token), and `verdict_changes_share` (his
  `with_notes` and `changes` over all his verdicts of the window, lower is better) is a KPI. Part 2d of the retro text
  (`domains/loops/retro.ts`) groups them into recurring preferences and files a signal per preference seen twice or more, to
  write it into the repo's `AGENTS.md`, `apps/console/DESIGN.md` or the lead brief, with that KPI as the marker.

*A Spec that comes with the Issue* (issue 911). A filer that already wrote the Spec (`factory issue new --spec @file`, body
`spec` and `specTitle`) hands it over at filing: `fileNewIssue` stores it in the filing transaction as an artifact of the
new Issue (kind `spec`, revision 1, author `factory`, key `filed-spec:<issue>`, which is the only mark that tells it from a
lead's Spec) and plans the owner's review page; `spec` implies `checkpoint: spec`. No wait begins (the machine's waits start
from `working`): the Issue settles and queues as any Issue, and `orderQueue` gives it the queue reason `spec` while the
latest revision of that Spec has no verdict (`OpenIssue.specPending`, read in `read/planning.ts`; a held incident stops no line). A
verdict on it (the owner's, or the factory's `looks_good` after 24 hours: `recheckReviews` also looks at a filed Spec whose
Issue is settling or queued) records only its note (`giveVerdict`, `noted`), since there is no wait to end; the Issue is
then admitted and the lead's brief has a Checkpoint section naming the artifact and its verdict instead of the order to
submit one. The ship gate counts it like any Spec. A lead that finds it wrong revises it (`artifact revise`).

Improve counts `specs_per_100` and `owner_decisions_per_100` (trend only), so a silent path shows as two near-zero lines.

## Loops and agw

A loop is a named tick (`app/loops/runner.ts`) with a trigger (an interval, or a kick when something changed), a budget
and single-flight passes. Its deterministic part runs in the server; its judgment is a dedicated agw workflow with its
own prompt, tools and skills (`agent-workflows`), called through the agw port with an idle watchdog (`AGW_IDLE_MS`, 10 minutes: an `agw` process that prints nothing and does not exit for that long is killed with its process group; `agw` ends a pending wait every 110 s, so a run that is alive, however long, is never cut by the clock, `rules/agent-limits.md`). A call is
recorded in `loop_calls` under its key, so the next boot takes it up again. The clock runs from the loop's last pass, not from
boot (`loop_passes`, written at the end of every pass): the first pass after a restart comes when the interval since the
last one is up, at once if it never ran, so a 6-hour loop still passes on a server that restarts on every deploy.

Five workflows (`factory-ask`, `-triage`, `-steward`, `-queue`, `-hygiene`) catch a model failure inside agw and answer with a neutral
result whose reason starts "<name> unavailable:". The adapters of those five (`adapters/agw/unavailable.ts`) read that reason: such an
answer is a failed call (`gone`), so the Judge's tries, the loops' rounds and retry windows run and nothing is recorded as asked,
settled or paged on it. Until agw lets those runs fail, the reason is the only mark.

## Perimeter

The API stays loopback. The door and the Console are published on the tailnet by dotfiles-private's `tailscale serve`
rows (the Console on :8797, to its loopback listener), and the perimeter is the tailnet ACL by device tag (a grant of
`tag:mac` and `tag:phone` to `tag:devhost` on tcp:8797), as Collie's (NL25); the deploy publishes nothing. There is no
per-request identity: anything that reaches :8797 reads what the owner reads, and no more than reads and the owner's fifteen write
verbs below, never a session start. The door holds only its own token; the orchestrator's is the owner's rights minus nine owner-only routes, and the Console proxy never uses it. Nothing that can start Claude Code is reachable from
another node. The Console listener reads, and forwards exactly the owner's fifteen verbs, his eleven answers, a collection's pin and unpin and an account's mode set and clear (a Decision's answer, an artifact's verdict and its needed-me mark,
annotation and its edit and delete, an Errand done, an Errand approved, a held signal promoted or dismissed), guarded against a cross-site page (JSON only bar a delete, no cross-site fetch
metadata, no foreign `origin`, 64 KiB); it starts no session and cancels or reopens no Issue, and promote files one only
from a signal already held and dismiss files nothing. The artifact frame (`/frame.html`, `/frame/*`) is the one document the page frames and is
served under its own CSP (scripts, no network, sandboxed), not the page's, whose `script-src` stays `'self'`.

One database, schema `factory`; migrations apply under an advisory lock and a checksum. The cutover imported Issues,

An Issue's and a session's `insights` join the usage schema at read (`read/usage.ts`, never copied; Issue 1790): tokens, cost, models and subagent sessions of the Claude sessions a lead's hooks reported (`payload.claudeSessionId`, with their `<session>:<agent>` subagents) per attempt, and for the Issue those plus any session the usage side tagged with its number, each counted once; from `usage.sessions` and `usage.records_unique`, the two relations the `factory` role may read. `partial` is true while a lead is alive, a lead that took turns has no usage row yet, or the schema cannot be read (then cost is null and tokens stay zero, which the Console shows as dashes). `windowPoints` comes only with one Issue's read (the window-share view is slower); `toolCalls` is null until the usage side counts them (signal to usage-tracker). `idle_seat_hours_per_day` leaves out the idle hours behind a drained queue, which are an owner or orchestrator state and not capacity going unused, `idle_seat_hours_drain_per_day` is that share and `idle_seat_hours_with_drain_per_day` the figure as it was before the split, kept until the first clean window so a ledger entry filed against the old one still compares; A repo whose CI cannot be read is under `build.unreadable` with the reason and keeps its check figures. Its two totals, `check_minutes_per_issue` and `ci_p50_minutes` (the pooled median of every run read), are in `build.figures` and appended to `capacity.figures`, so the ledger measures them. The retro's part 2c reads `build` and files speed-ups per repo. A retro marker may name a figure key as its `kpi=`, so the ledger checks the last capacity change against the window (Issues closed per day must not fall); `capacity` is null on a server with no capacity settings.

**The queue order for throughput, and the edges the factory added** (`orderQueue` in `domains/planning/queue.ts`, `domains/loops/edge-need.ts`, `kernel/edge-need.ts`, `read/edge-need.ts`, `app/loops/queue.ts`; `migrations/1047_queue_edge_removals.sql`). The admission order keeps its first rules: an incident of a stopped line, then Issues with no open blocker, then the owner's `prio`. Inside one project and one `prio` the places the first rules gave are exchanged among that project's Issues so that what finishes sooner starts first: triage's size (small, medium, large; an Issue with none reads as medium), less one size for every 6 hours the Issue has been in the queue (`AGEING_STEP_MS`, never below small, so a large Issue is passed for 12 hours at most), then the position in the newest order `factory-queue` answered for the repo (`PlanningStore.queueOrder`, read from `queue_asks`; an Issue it did not place comes last), then the lower Issue number. The owner's `prio`, the chain and the way projects interleave are never touched, and the request to `factory-queue` now carries each Issue's size. **Taking edges back:** every pass of the queue loop first reads the edges the factory added that still hold a queued Issue (`planning_edges.inferred_by` set, by triage or the queue loop; an edge a filer or the owner stated has none and is never read) and takes one back when both Issues shipped (an accepted ship's `commits` evidence, `paths`) and no meaningful path is in both (`docs/plan.yaml` and the lockfiles are left out), or when its blocker has waited on the owner (`decision`, `review`, `errand`) for more than 6 hours (`OWNER_WAIT_MS`, `ownerWaitMs`). The removal goes through `removeInferredEdge` (planning): one transaction keeps what the edge carried and why in `factory.queue_edge_removals` (kind `disjoint` or `owner_wait`, the reason in words), drops the edge and notes it on the Issue. `checkQueue` never adds a pair that was taken back. Disjoint files can only be seen after both Issues shipped, so the sweep is rare on an edge whose Issues have not run yet: the measure below says whether that is worth more. **Measuring edges** (`readEdgeNeed`): for every edge the factory added in the window (the stored ones and the removed ones) whose two Issues both shipped, `needed` when the commits touched a file in common and `notNeeded` when not; an edge whose Issues did not both ship is `unknown`. `factory read capacity-loop` carries it as `edges` (per source `triage` and `queue`: `added`, `needed`, `notNeeded`, `unknown`, `removed`, `notNeededShare` and `stopped`, and the share over all sources) and Improve's Capacity section shows it as "Edges by shared files". **Stopping a kind:** once a source has at least 10 measured edges over the last 14 days and more than 60 % of them were not needed (`EDGE_STOP_MIN`, `EDGE_STOP_SHARE`), the queue loop refuses every edge it would add (the refusal says why) and triage settles an Issue with no edges (counted as `dropped`); the figures come back as soon as the share falls. Evidence with 100 paths (`EVIDENCE_SAMPLE_CAP`, where a ship's path list is cut) makes its Issue unmeasured, and the read's `stopped` is what the loops decide (the last 14 days ending with the window), whatever `days` was asked. A file-level overlap is a proxy: an edge for a reason the files do not show (a migration number, a behavior one Issue relies on) reads as not needed, so the threshold is a setting of the code, not a rule of the chain, and an edge somebody stated is never judged.

**What the queue waits for** (`factory.queue_intervals`, `migrations/1033_queue_intervals.sql`; `domains/capacity/waits.ts`, `recordWaits` in `app/capacity-admit.ts`). At the end of each admission pass the last look's reasons are stored per queued Issue, the kind `factory queue order` prints: an Issue's wait is a list of `(kind, from_at, to_at)`, a new interval begins only when the kind changes, and one ends at the pass that finds the Issue admitted, closed or without a reason (`to_at` is null while open; the wait is as exact as the pass interval, a minute). The memory gate says no for two reasons, and the learned lead-fit refusal (`Refusal.part: 'fit'`) is its own kind, `memory_fit`, the host's reading `memory`. Only the pass records: `factory queue order` is a read. The message of the interval is the reason's text when it began. Intervals are kept 400 days (`WAITS_KEEP_MS`, as the hourly class rollups; a few rows per Issue); a restart that leaves the server down counts as waiting. `factory read capacity-loop` carries `queueByReason`: per kind the hours Issues were queued (intervals clipped to the window), the Issues, the idle seat-hours that fell in minutes a wait of that kind was open, and `byRepo` (the queued hours and Issues split by the project the interval was recorded under, most hours first; the idle seat-hours are not split by repo), which names the repos whose `leads: N` binds a `claim` and which the Console's Improve page lists beside each reason in its Queue waits table; every caller but the owner and the orchestrator sees the work repos' shares summed under one redacted name. A minute's idle seat-hours are split equally among the distinct kinds queued in it, leaving out the kinds that are no cost of the factory (`chain`, `line`, `finalizing`, `spec`, `unknown_project`) unless only those wait; a minute no interval covers is `unrecorded`, so the kinds sum to `idleSeatHours`. `idleSeatHoursDrain` is the `drain` kind's share of `idleSeatHours` (total and per day; the same split, so it equals that kind's `idleSeatHours` here), and the Console's idle card shows the rest. `idleSeatHoursMemory` stays the swap-based cut of all the same hours, drain included; the lead-fit refusal shows only in `queueByReason`.

`GET /v1/throughput?hours=N` (`factory read throughput`, N 1 to 336, default 24, else 422) shows where the host's memory and CPU went, computed in SQL by `read/throughput.ts` over `[now - N h, now)` from `host_samples` (the minute's signals), `host_class_samples` (the per-minute class rows) and `host_process_samples` (the notable processes). `host.minutes` is the count of distinct minutes with class rows. A key's per-minute total is the sum of its rows' `footprint_mib` and `cpu_ms` at that minute; its `footprintMib` is the sum of those totals over `host.minutes` (a minute it is absent counts 0), `peakMib` the largest total, `cpuSeconds` the summed `cpu_ms` (nulls ignored) over 1000, `cores` that over `host.minutes * 60`. `byClass` always lists the seven classes, `byRepo` the top 20 repos of lead and step rows with `leadMib` and `stepMib`, `byTenant` the top 20 tenants, `topProcesses` the 15 largest by peak, grouped by name, class, repo and tenant. `signals` holds the pressure-level minutes (normal, warning, critical, unread), p50 and extreme of load, idle, user, system and busy CPU (`cpuBusyPct`: user plus system, else 100 minus idle), memory and swap in use as bytes (`memoryUsedBytes`, `swapUsedBytes`), compressor, swap share and process count, the swap volume's free space, and `collector` the CPU the collector's own children took. `host.now` is the newest minute of the window as amounts for the page's host row: busy CPU, load, the load ceiling that minute stored, `cores` (the server's, `ReadModelDeps.cores`; null where unknown), the RAM, memory and swap in use and the swap's size in bytes, and the pressure level (null with no minute); a minute stored before `migrations/1044_host_bytes.sql` has no bytes, so its memory and swap are read as their share of the newest known RAM (the SQL's `ram` and `m`, written out in each host query). The `timeline` points carry the busiest minute of each bucket for pressure, swap share, busy CPU, memory and swap bytes and load: the page draws five charts from them. Tenant and repo names include work repos: the owner and the orchestrator read the model whole, a lead (the agent token) reads it through `read/throughput-redact.ts`, which keeps every figure and turns the names of work repos and tenants into `private` (a work repo's flaky tests are dropped), and the read token has no row. `apps/server/test/read-models/throughput.test.ts` restates the figures over seeded rows. `tests` carries the test runs: `byProject` per repo with a `step_costs` row in the window (by its `at`, the end of the run): `runs`, `failedRuns` (exit code present and not 0; a run killed at its limit is 124), `runMinutes` and `failedRunMinutes` (the summed `duration_ms` over 60 000: the slot-minutes failed runs cost), `testResults`, `flakyTests` and `flakeRate`; `flaky`, the 20 tests with the most flaky commits. A test counts once per run (failed when any of its results failed). A **flake** is a test with both a pass and a fail at one commit over clean-tree runs (`dirty = false`: uncommitted changes are not the same code; skipped results and runs with no commit are left out); `flakeRate` is the flaky (test, commit) pairs over the pairs seen in two or more clean runs (null when none), `firstFlakeAt` the later of the pair's first pass and first fail. A test that fails every run at a commit is broken, not flaky. `apps/server/test/read-models/throughput-tests.test.ts` restates both over seeded rows. Three more parts serve the Console's Throughput page (`apps/console/src/routes/throughput.tsx`, `tp-console`): each `byClass` row carries `share`, its part of the footprint of all seven classes (only the tenant class has a budget, shown beside the tenants as `host.tenantBudget`: the owner's verdict on the page's Spec was that fixed shares of RAM would be friction, so the page draws no other threshold on memory); `host.timeline` holds the window in equal buckets (5 minutes up to 24 hours, 15 up to 72, else 60; a bucket with no sample is left out) with the worst pressure level and the largest swap use and load of each; `improvements` lists the 50 newest rows of `throughput_findings` (before, target, after, status, Issue), whatever the window. The page reads the three windows 24 h, 7 d and 14 d (`?hours=`, the window in the sidebar) and shows the stat row, memory by class, the pressure, swap and load charts, tenants, projects and processes, the lead time split with the longest Issues, the project scorecard and the improvements. The weekly retro's bundle carries the same figures as `RetroModel.throughput` (the window capped at 14 days; classes with shares, signals, the lead split without its Issue list, the scorecard and the improvements; numbers and project names only, so the redacted bundle keeps them), and part 2e of the retro text reads them.

The same answer carries `series` and `stored` (`read/throughput-series.ts`, `apps/server/test/read-models/throughput-series.test.ts`), both derived from rows already stored, never a counter of their own. `series` is a point per bucket (the host timeline's: 5 minutes up to a day, 15 up to three days, else an hour) with the counts read at the bucket's start: `running` (attempts in `lead_attempts` started and neither marked gone, which only a lost lead is, nor ended by the first close of their Issue after the start) in total and `runningByRepo`, `queued` (Issues in an open `queue_intervals` row) in total, `queuedByReason` (the interval's kind) and `queuedByRepo`, and `peakRunning`/`peakQueued`, the maxima of the host's minute samples (`leads`, `queued`) in that bucket, which see a state shorter than a bucket; the reason and repo splits begin where `queue_intervals` begins. A lead's read sums the work repos under `private`. `stored` is the oldest and newest row of each source (`host_samples`, `host_class_samples`, `queue_intervals`, `lead_attempts`, `step_costs`, `merge_windows`) whatever the window or the epoch, so a window the epoch cut says which earlier data still exists. `project[].slot` carries `waitMaxMs` beside the p90 and `mergeLock` its p90 and maximum wait in minutes. `GET /v1/sessions` takes `limit` (default 200, at most 1000) and `before` (an ISO instant): the newest attempts first, `next` is the `before` of the following page and null once the oldest is reached; an Issue's own list is whole.

The same answer carries `lead` and `project` (`read/throughput-account.ts`, `apps/server/test/read-models/throughput-account.test.ts`). `lead` is each Issue closed in the window (an applied event into `closed`, one row per close, so a reopened Issue is two) over its lead's wall time, from the start of its first lead after the Issue's previous close to the close; an Issue whose lead never started is not in it. The wall is split into seven places that add up to it: the owner (the Issue waited on a person: reasons `decision`, `review`, `errand`, or `external`, another person's review of its pull request, read from `issue_events`), a step (a `slot run` ran), a slot (one was queued), the merge lock (queued for the window), CI (a run of the lead's branch was queued or running) and a turn (the model worked, from `turn_started` to the next turn end, API error, session end or lost pane of `lead_hook_events`; a compaction does not end one), and idle, the rest. Each place is a set of ranges inside the wall and takes only what the places before it, in the order above, did not, so no second is counted twice and a wait that fell inside a turn is the wait's. A step or a merge window is the lead's when its directory (`step_costs.cwd`, `merge_windows.cwd`) is inside the lead's worktree; a step row from before the column carries the worktree's `factory-<issue>-<attempt>` in its name instead. A `factory merge-lock` reports every finished call (`POST /merge-windows`, after the command and the release, best effort: when it asked, when it got the window, when it gave it back, the exit code) to `factory.merge_windows`; wait is asked to got, hold is got to gave back, and only the wait is a place of the lead's time (the hold is the lead's own rebase, push and CI). `project` is one scorecard per repo that closed an Issue, ran a step, finished a CI run or took the window: the steps of the repo (slot minutes in total and per closed Issue, the wait for a slot with median and 90th percentile, the largest peak memory, failed steps and their minutes), the check by tier (`check-fast` is `fast`, `check` is `full`, any other step its last word) with median and 90th percentile, the CI runs read into the ledger (success, failure and timed out; minutes, queue minutes, median and 90th percentile of a run, failed runs and their minutes), the local to CI split (host minutes against CI minutes), the merge windows (count, wait and hold minutes) and the lead time split summed over the repo's Issues. The test restates the split in plain SQL by walking each wall minute by minute and putting every minute in the first place that covers it.

**The project screens** (`read/project-page.ts`, `read/project-index.ts`, `packages/contract/src/project-page.ts`, no table of their own): `GET /v1/projects` (`factory read project-index`) is the Projects table's one read: every project in the owner's Herdr groups (the Herdr app's `groups.json`, read on every call from `FACTORY_PROJECT_GROUPS_FILE`, default `~/.config/herdr-app/groups.json`; an unlisted project or an unreadable file is Other), the digest's counts, the Issues in Watch, shipped per hour over 7 days and the newest ship, the cycle and queue wait medians (the KPIs' definitions) of the last 7 days against the 7 before, open incidents and the newest regression of 7 days, plan rows done of all (done as `rowStatuses` says), running leads with the project's own cap, its newest hygiene pass (probes clean of run, the oldest finding still raised within 30 days) and newest digest, and the host's seats now; `GET /v1/projects/:name` (`read project-page`) is one project's page: the counts, the Issues shipped in the last 7 days (the newest 100) with their daily and hourly counts and the 7 days before, and the production facts the factory stores: Issues in Watch, incidents opened and regressions in the last 7 days, and the door routes that file a monitor's alerts (Uptime Kuma, ClickStack) in the project with the last event each heard. `GET /v1/projects/:name/setup` (`read project-setup`, `read/project-setup.ts`) is the `project.yaml` in force as a form: each key of the schema in its order with the schema's own description (`.describe()` on `ProjectFile`, turned into JSON Schema by the route, so `read/` holds no domain code), the value stored (defaults filled in), whether that is the default, and the file as YAML; the Console's Setup tab renders it. `GET /v1/projects/:name/hygiene` (`read project-hygiene`) is the hygiene loop's record for the project: each built-in probe and each the project declares (`hygiene.probes`) with the newest pass's run of it (or the project's reason for opting out, or "never run"), the newest pass (commit, judgment, the documents found stale and recently edited) with its findings and how each ended (`filed`, `left_out` by the cap or a held class, `refused` by intake), and the last five passes. A pass is found by the project's name, its path or a worktree below it. The read token is told 404 for a work project, gets no work project in the list and no monitor names. The Console reads the plan rows from `GET /v1/projects/:name/plan` and the open Issues from the cached flow model, so the page adds no second copy of either. `apps/server/test/read-models/projects.test.ts` restates every figure over seeded rows.

**The counting epoch and the three answers.** `config/throughput.json` holds one ISO time (`FACTORY_THROUGHPUT_FILE` points elsewhere; a missing or bad file stops the start, so no read quietly counts everything). Nothing before it counts: `readThroughput`, `readCapacityLoop` (so `factory read throughput`, `factory read capacity-loop` and the retro), the friction read (`readFriction`: its window, its comparison window and its evidence), the daily ranking's window facts (`readWindowFacts`, the budget facts) and the lead costs start at `max(asked start, epoch)` (`kernel/epoch.ts`). A window it cuts short says so: `epoch` is `{at, cut, countingSince}` and `window.from` is where the counted window really starts; the capacity loop's `days` is the days counted. A median over earlier days waits for 3 days after the epoch (the per-Issue slot-minute baseline needs 3 days with a closed Issue; the tenant median keeps its stricter 7), and the ranking files nothing from a window under a day (`MIN_RANK_DAYS`; its pass notes "ranking waits"). No row is deleted: retention removes old rows on its own and moving the epoch back is one line; deleting them with a migration was the alternative and was not chosen because it cannot be undone and the rows are the evidence for comparing the host before and after its setup changed. An open or shipped improvement filed before the epoch reads `unmeasured` with `reason` "filed before the counting epoch" (derived on read; the ledger pass does not measure it). `answers` (`read/throughput-answers.ts`, also the first field of the retro's throughput block) is the three questions the Console's Throughput page opens on, each with one sentence the server writes, a figure and a trend: `host` (is the host the limit: the newest pressure level, swap and memory read, and the queue's own text when an Issue waits for memory, which names the free memory against what the lead takes), `queue` (the reason with most queued hours from `queue_intervals`, `memory_fit` counted as memory, the kinds that are no cost of the factory left out, with its hours per UTC day and every reason's hours) and `cost` (the tenant class when it is over its budget, else the open improvement with the most minutes, else nothing). Everything else on the page is a detail one step below an answer.

## The throughput loop

**The throughput loop** (`tp-loop`; the measures are `GET /v1/throughput`'s and `read/throughput-loop.ts`'s, the table `throughput_findings`, `migrations/1027_throughput_findings.sql`). Measured costs only pay off when someone acts on the largest one and checks that it moved. Once a day, without a model, the loop ranks what cost most over the last 7 days, in minutes of the host's capacity: a project's slot-minutes of failed `factory slot run` steps (`failed_run_minutes`, a per-day figure); slot-minutes per Issue closed `done` when it is 25% above the median of the same ratio per day over the 14 days before (`slot_minutes_per_issue`, cost the excess times the Issues closed); a step tier whose 90th percentile peak memory is over the project's `budgets.peak` (2 GiB when it sets none), cost the minutes of the runs over it (`step_peak_mib`); a process (not `postgres`, `SHARED_MEMORY_PROGRAMS`, not `kernel_task`, `isKernelTask`, not `XProtectRemediator*`, `isTransientScanner`, and not of the tenant class, which `tenant_growth_mib` below reads) whose footprint grew by 1 GiB or more between its first and last notable minute, cost its notable minutes, on the repo it belongs to or on software-factory (`process_growth_mib`); and the minutes queued Issues waited, one candidate per binding reason read from the queue intervals (`queued_minutes`, the subject the reason; "What the queue waits for" above): `memory` (interval kinds `memory` and `memory_fit`, the label names the share of the lead-fit refusal) and `account` (`window`, `cap`) are filed on software-factory with the repos they hit most, `claim` and `lane` on the repo whose Issues waited, naming its `leads` and the lanes (with their caps) its Issues waited in (`WAIT_SUBJECTS`, `waitFacts` in `read/throughput-loop.ts`). A wait behind an `after` edge, a stopped line, a Spec at the owner, a drain, the boot grace or the load is not ranked (`queue_capacity_share` in `factory read kpis` is still the cut between an `after` edge and capacity, and `queueByReason` shows every kind). A finding filed before the reasons were recorded (subject `*`) is `unmeasured` at its after. A cost under 30 minutes is not a finding. A cost the newest 3 days already left behind (its figure over them is at or under the target: fixed days ago, or a burst that ended) is not filed, though it still sits in the 7-day total; a figure those days cannot give (no run, no closed Issue) says nothing and the candidate stands. Two findings read the tenant class (launchd jobs and VMs) from the hourly rollups `host_class_hours` (complete hours; a cluster's shared mapping is counted once, as the class rows store it), both filed on the repo that owns the host's configuration (`FACTORY_TENANT_PROJECT`, default `dotfiles`) because a tenant is a job or VM no project's lead can shrink: `tenant_class_mib`, the class's mean footprint over the 7 days above its budget (`FACTORY_TENANT_BUDGET_MIB`, default 6144, what the dotfiles program aims at with its work profile up; target the budget), filed with the three largest tenants and their figures; and `tenant_growth_mib`, a tenant whose mean over the newest 24 hours is 1 GiB or more above its own median of the 14 days (24-hour buckets of sampled hours, an absent tenant counting 0, at least 7 buckets or no median) before them, which needs no budget and no list of tenants and catches a VM left on (subject the tenant, target that median). The excess is turned into minutes as slot-minutes: the excess over 2048 MiB (one test slot's default step budget) times the minutes it was held, the 7 days for the class and 24 hours for a tenant, so standing memory ranks against the other costs. The after of both is the same mean over the 3 days past the ship. They hold the repo like any finding: one open at a time. Only the class kinds read a budget: the other classes have none (the Console's Throughput page shows each class's share, and the pressure level and swap carry the state); `GET /v1/throughput` carries `host.tenantBudget` (the budget, the window's tenant footprint, `over`). Per project, with no improvement open, the largest cost that no finding holds is filed as a signal on the project's repo (`agent:<project>`): the measured before in the figure's unit, a target (half of a time figure; the median for the per-Issue ratio; the peak budget for a step), the query that reads it again, and the retro marker (`Retro: <date> kpi=<kpi> before=<n> direction=down`) as its last words, so the weekly retro's ledger lists it. At most 5 a pass. A project holds one open improvement: while a finding's Issue is not shipped, nothing else is filed for it.

**A binding cap and the disk fit** (NL48; `domains/loops/caps.ts`, `read/cap-facts.ts`, `domains/capacity/disk.ts`). A repo's `leads` or a lane cap is a claim about a resource, and the throughput pass checks it beside the ranking: when an Issue of the repo was queued for `claim` (or `lane`) in at least 60 minutes of the last 24 hours in which an account seat was idle (`host_samples.seats` over `leads`) and the cap is still below the default, it files one signal on the repo (`The lead cap \`leads: N\` of <repo> binds while seats idle`; the cap and the repo are its finding key, so one open signal per cap) with the cap, the comment beside it in the default branch's `project.yaml` (`capComment` of `@software-factory/project-lint`) and the figures for the resource the comment names (`capReasonOf` in `contract/project`: disk, merge windows, a lead's memory); the repo's `queued_minutes` finding for the same wait is not filed beside it. Disk is not a cap: the host loop measures each running attempt's worktree with its build output (`du -sk`, at most every 10 minutes per worktree and 3 per pass, `factory.worktree_sizes`, `migrations/1055_worktree_sizes.sql`) and admission refuses a lead as `disk` when the repo's learned footprint (p80 of the newest ten attempts, at least three) does not fit the home volume's free disk less the headroom (10 GiB or 5 %) and the footprints of leads started in the last 10 minutes (`diskRefusal`; `HostReader.disk`, `statfs`). With no lead running, no learned size or no reading it keeps nobody out.

The **ledger** is the table: a row per filing (`open`), marked `shipped` with the ship's time once its Issue shipped, or `dropped` when it closed without a ship (the subject is left out for 14 days). Three days after the ship the loop reads the same figure over `[shipped, shipped + 3 days)` (`figureOf`, the same SQL as the ranking, so a figure is read one way) and stores the `after`: `moved` when it fell by 10% of the before or more, `flat` or `worse` otherwise, `unmeasured` when the window has no run, Issue or step of the subject. A finding that moved is held out of the ranking until the 7-day window has left the days before its ship; one that did not move is ranked again at once and filed with the earlier attempt named (`reopens` is that row), because its cost is still there. The weekly retro's ledger (`read/retro.ts`, `ledgerOf`) joins the table by signal: its `now` is the loop's own after and its `measured` is `after`. A reading that fails (the database, a slow query) is a note in the pass and leaves the row for the next day.

`budgets:` in `project.yaml` (`{ fast: 90s, peak: 2GiB, fail: 10% }`, each optional, a duration, a size, a share; `budgetsOf` in `packages/contract/src/project-file.ts`) makes a breach a signal the day it happens (`fail` the second day in a row, a red `check-fast` not counted), through the `selfwatch` loop above, not the daily pass. `peak` is also the step target of the daily ranking.
