# software-factory

The lifecycle server for agent-built software: it takes in signals and requests, merges duplicates, queues
work against the available Claude Code subscriptions, starts interactive Claude Code sessions in herdr-core terminals that
own a piece of work from root cause to production evidence, follows them through hooks, and closes and
learns. CLI `factory`. Status: being planned and built; `docs/program.md` is the current state.

**Start here:** `docs/decisions.md` (what was decided and why) → `docs/program.md` (tracks, who runs them) →
`docs/design.md` (the design) → `docs/research/` → `docs/evidence/` (the golden set and the
intervention KPIs, moved from dotfiles; `README.md` there says what still re-runs).

## Rules

- **Public repo.** No secrets, hostnames, IPs, tailnet names, internal URLs or account e-mails in any tracked
  file. Placeholders: `<your-domain>`, `<see-1password>`. Secrets resolve at runtime through `secrets-run`.
- **The factory never calls a model.** Every judgment (classify, dedup, wording, learnings) is an `agw`
  workflow; the factory calls `agw` like any other client. No model SDK in this repo.
- **Dependencies point one way:** factory → agw, herdr-core, GitHub, the intake sources. Nothing here is imported
  by agent-workflows.
- **Facts are stored, state is derived.** "Working", "stuck", "waiting" are computed from events when read.
- **Every effect has a deterministic key** (pane names, prompt ids, comment markers), so a replayed tick
  never spawns, prompts or posts twice.
- **Interactive Claude Code in herdr-core only.** Never headless `claude -p`.
- **CLI contract = agw's:** `--format json|plain`, data on stdout, messages on stderr, the same exit codes,
  never prompts.
- Bun, TypeScript strict, zod at boundaries, exact pins (no `^`/`~`; `~/.bunfig.toml` enforces a 3-day release-age
  cooldown, never exclude a package from it). No Effect: the F0 spike decided that
  (`docs/spikes/2026-10-30-effect/verdict.md`).
  The effects are in `docs/design.md` §3 "As built".
- **Never call a port inside a transaction.** The tick claims a row and commits, calls the `Runner` (every call has a
  process timeout), records the result in a new transaction. A failing start is retried until the 30-minute budget, then
  `failed` with a logged reason; `factory spawn requeue <key>` starts it over. Admission is decided again at every claim.
- **Trust boundary.** The token can start Claude Code with `--dangerously-skip-permissions`: a spawn's `repo` and `space` must be
  inside `FACTORY_REPO_ROOTS` after `realpath`, else 422 and nothing stored. The API is loopback only; the tailnet and the
  owner's GitHub user are the perimeter. `FACTORY_REF=<branch>` deploys that branch, the same boundary.
- **The door** (`packages/door`, `docs/design.md` §11): alerts from the tailnet become Issues. It binds loopback only, holds no factory token
  and no database credential, and posts to the socket's `POST /intake`; the repo comes from `factory.door_routes`, never the payload.
- **Hooks: spool first, then post.** `factory hook <event>` does nothing without `FACTORY_SESSION`, appends one line to the
  spool, posts it to the unix socket (300 ms) and exits 0 whatever happens (one exception: the Stop send-back, exit 2).
  `src/hook.ts` imports only `node:fs` and `@software-factory/contract/spool` (no zod, no rest of the CLI) and keeps
  **stdout empty for every event, and stderr too except for a send-back**: Claude Code injects a hook's stdout into the
  session's context. The one exception is a `session-start` with `source: compact` in an Issue lead's session (`lead-<issue>-<attempt>`): one line telling it to re-read the Issue. The socket (mode 0600) is the hook's credential; the witness alone records `runner_restarted` and
  `pane_gone`.
- **Placement and sessions.** The Runner looks before it acts: a terminal carries `factory.key=<spawn key>`, and a live one
  running claude is never started twice. One space per repo, keyed by path; every repo in `FACTORY_SPACES_FILE` (inside `FACTORY_REPO_ROOTS`) has a `plan:<name>` shell tab, a reconcile (`spaces.ts`, every 10 min) that never closes it (`HcRunner.close` refuses a `plan:` key; it is no spawn). Every spawn is a
  tab (any role, with or without a parent): there is no child or hidden placement. `spawns.placement` stays in the schema, is no longer read or written, and an old `child`/`hidden` value reads as a tab. State is derived from stored events, never stored.
- **Roles** (`config/roles.json`): role → tier (`haiku|sonnet|opus`, never a model id) and effort. `lead` (sonnet, high) is the level every Issue lead runs at, whatever Classify asked. The table is `lead`, `implementer` (the `spawn create` default), `verifier`, `reviewer` (sonnet, medium: review v4's read-only session) and `Explore`; a stored spawn or session with an older role (`mother`, `wave`, `worker`, `mechanical`, `deep`) still reads, a new spawn with one is 422. `rd --role` depends on `factory role get <role> --format json` printing exactly
  `{"role","tier","effort"}`; unknown is exit 4. Values change only on measured data.
- **One process.** A session-level Postgres advisory lock is taken first; a second copy exits 1. Every advisory key lives in
  `src/locks.ts` and they stay distinct.
- **One contract.** Response shapes are zod schemas in `packages/contract`; the server builds every body through its schema and
  the CLI parses with the same one (a body that does not parse is exit 9).
- **One schema, `factory`,** in the shared database; migrations are advisory-locked, qualify every name, and are expand, then
  contract. The `factory` role has no CREATE on the database; `DATABASE_URL` comes from `secrets-run`, never a tracked file.
- **The API is authenticated.** Every route but `GET /health` needs `Authorization: Bearer <FACTORY_TOKEN>`; JSON only (415), at
  most 64 KiB (413), loopback Host (421). The CLI reads `FACTORY_TOKEN`; run it under `secrets-run run --env-file=.env.tpl --`.
- **Tests:** `make test` runs through `factory slot run` when `factory` is installed (a lease; open only when the server is down, a wait past 45 min exits 75 without running). Update this file in
  the same commit as the code it describes; behaviour goes to `docs/design.md` §3 "As built", not here.
- Direct-to-master, conventional commits, no AI attribution.

**Issues** are `docs/design.md` §4: `src/issues/lifecycle.ts` is the one writer of `issues.state` (a create, always `queued`, is `create.ts`; the door's `intake.ts` files through it); past about 500 lines, stop. `FACTORY_AGW_BIN` is the `agw` Classify calls; `FACTORY_ASK_JUDGE=off` sends every ask to the owner (default on); `FACTORY_ALERT_LEADS=0` keeps `alert` Issues from starting a lead (default on); `FACTORY_LEADS_PER_ACCOUNT` (default 2) caps live Issue leads per account in admission (a program lead, a wave and a lead whose Issue waits on the owner's decision are not counted); `FACTORY_LOAD_CEILING` (default 60) holds every new Issue lead (hold `load`, health line `held by load`) while the 1-minute load average is above it, running leads are never touched (`admission.ts`); the lead's brief opens with the operating contract (`STANDING_ORDERS`, hash pinned by a test), and the lead opens no terminals; `FACTORY_ARCHIVE_DIR` is where a closed attempt's transcripts go (default `~/.local/share/factory/archive`). `issue_id` goes on a lead's session only. **Every park can end** (RS3, `docs/design.md` §4): the lead's own next turn ends an `unreported` park (as a wall's session ends a `wall`); a `lead_gone` queues the Issue again for the next attempt (finalize first), twice, the third parks; a Stop whose `background_tasks` has an unfinished entry is neither sent back nor parked; a red verify is retried up to three times (`…:retry1..3`, due 1, 2 and 4 min after the previous red) before it is a `regression`, and the third regression parks the Issue (`parked`). A permission prompt of an Issue lead (`lead-N-M`) is never an owner ask: after 15 min it is one health line naming the command, and nothing is typed. An Issue waiting on a `decision` that holds a repo's claim while another Issue has been queued behind it 15+ min gets one health line (`health.ts`). The counts are read from `issue_events`, nothing is stored. `git` and `make verify` never run on the tick or in a transaction: a lead's call waits for its `git`, and `verify` and `finalize` run off the tick (`issues/offtick.ts`). Evidence kind `review`: `ship` also asks agw (`agw review route` for the tier of `<worktree cut sha>..landedAt`, `agw review covered` over the same range; `issues/review.ts`, `derive` stores `derived.review`). It is required when the tier is not `none` and met only by agw's coverage (every first-parent commit reviewed at its tier, no open important finding), never by a filed `--kind review --link`. An agw failure refuses the ship (fail closed). `close` is not asked. `factory.issue_facts` (migration `033`) is a view: one row per attempt, the attempt derived from the `admitted` events, no usage read, no review rounds (`docs/design.md` §4 "Issue facts"). **Dependencies and priority:** admission looks only at an Issue with no `issue_deps` row (a close deletes its rows, so a row is an open dependency) and orders a project's candidates by the latest `prio` event (none = 0), then id, so a blocked oldest holds nothing back; `issue new --after <id>` writes the rows in the create's transaction (an unknown or closed id: 422, nothing stored; a repeat of a `--key` ignores `--after`), `issue prio <id> <n>` files the event, and nothing is stored on the Issue.

**The steward** (`src/issues/steward.ts`, `docs/design.md` §4 "The steward"): once per tick, after the timers and before the inbox, it files inbox events for a stalled Issue and never moves state itself (a model is never called; the one new edge is `restart`, a `lead_gone` park to `queued`): a wake `note` for a `blocked`, `parked` or `unreported` Issue whose lead is live (a block naming the verification re-runs it off the tick first), a nudge `note` for a silent or over-budget lead (a lead whose last event is a stop with background work in flight, `leadsOnBackgroundWork`, is not silent), a `restart` for a `lead_gone` park, the holder's wake when an Issue has queued 15+ min behind its claim (never for a `wait` holder within `WAIT_GRACE_MS` of the wait or before its `wake_at`). Backoff 30 min, 2 h, 6 h from when the cause began, at most 3 acts per Issue and cause (keys `steward:<issue>:<cause>:<n>`, counted from the inbox, nothing stored); then one `steward_exhausted` event; the ask judge (below) then answers it with a `note` or records the one outbox line `notify:steward:<issue>:<cause>`. `factory status` shows `steward { acts, exhausted }`. A `note` prompt for a `lead-…` session pending 5 min while the lead is `working` is typed anyway (`Runner.type` `force`), proven by a `turn_ended` too. A `needs a human` review line is gone once the job was taken, its repo has no open Issue, or it is a day old.

**The ask judge** (`src/issues/judge.ts`, `judge-input.ts`, `agw-call.ts`; `docs/design.md` §4 "The ask judge"): each new decision and each `steward_exhausted` event is judged by `agw factory-ask` off the tick before the owner hears of it (`recordDecision` and `exhaust()` no longer notify; the pass sends `notify:ask:<id>` / `notify:steward:…` once). Verdict `answer` passes the guards (one of the options, a source, a declared default only if `isDoNothing`) and is filed as an inbox `answer` from `steward` (`judge:<id>`), reversible by an owner note. Owner, any failure, `FACTORY_ASK_JUDGE=off` (default on) or no judge: the ask stands as before. A visible (IuRoot) repo sends nothing to `agw`. A new ask is hidden from `attention` until `ask_judged:<id>` exists, for at most 45 min.

**Asks and health** (RS3, `docs/design.md` §3 `factory status`, §11 "The fleet view"): an ask is a decision only (`decision`, an Issue `blocked`, hc's `blocked` prompt, a `wait` on the owner, the human queue). Everything else that needs a look is a health line, never an ask: every park with reason and age, `stuck`, `walled`, failed spawns and notes, undelivered notifications, a lead that did not start, a silent lead (no event for 20 min), an Issue over its size's budget (s 2 h, m 6 h, l 24 h), two regressions. `factory status` has `attention` (asks) and `health`; `/fleet` has `asks` and `health[]` (`src/health.ts`: the derived lines, `healthKind`, and the `heartbeat` on `GET /health`, `{ok, reason, tickAt, queueMovedAt}`, whose names a pusher reads: do not rename them). A line is in one list. **A line about something finished ends 72 h after it finished** (`FINISHED_HEALTH_MS` in `src/health.ts`: a failed spawn, a failed note, an undelivered notification, a kept worktree); an ongoing one stays while true. Derived at read, nothing stored.

**The fleet view** is `docs/design.md` §11 "The fleet view": `src/fleet/` (`index.ts` the builder the tick kicks, `model.ts` the pure assembly, `sources.ts` hc and the human queue read-only, `place.ts` which places are IuRoot's, `store.ts` the one-row snapshot `factory.fleet_snapshot` and `NOTIFY fleet`, `digest-model.ts` where the digest meets the model), `GET /fleet` and `POST /fleet/refresh` (**token API only**: the model holds IuRoot's text, so the socket answers 404), `factory fleet` (needs `FACTORY_TOKEN`, exit 3 without). The model is slim and read-only: repos with their live sessions, `issues[]` (the open Issues), `asks[]` (hc blocked, a wait on the owner, factory, decision, the human queue, the digest's `reply`), `health[]`, `summary`, `queue`, `quota`, `errors`, `digest`. It has no plans, git state, tiers, actions, presence or reaper (Reset row 8; their tables stay until row 9). The model itself reads and calls no model; **the digest** (`src/fleet/digest*.ts`, `transcript.ts`; `docs/design.md` §11 "The digest") asks `agw digest` about what changed every `FACTORY_DIGEST_EVERY` (default `5m`, `off`) and the snapshot reads its cache (`headline`, `short`, `source: reply` asks); **nothing of a `visible` (IuRoot) repo or session is ever sent** (`scopeOf` is the one place that decides). Config: `FACTORY_VISIBLE_ROOTS` (read-only roots, default `~/IuRoot`, `off`), `FACTORY_ASK_HUMAN`, `FACTORY_DIGEST_EVERY`; `FACTORY_PROBE_HOSTS` and `FACTORY_REAPER` are still accepted by `env-file.sh` and ignored. The owner is always treated as away: only a decision, the steward's spent retries, the morning reading and a test go out (`notify/outbox.ts` `foldReason`); the 07:30 message is built from facts (Issues shipped in 24 h, the snapshot's asks, health and open Issues, no model text; `notify/digest.ts`).


**The read API** is `docs/design.md` §11 "The read API": `GET /v1/overview|issues|issues/:id|sessions|sessions/:id|asks|health|accounts|stream`, **token API only** (the socket answers 404 for all of `/v1`; it holds IuRoot's text and marks it `visible`). Schemas `packages/contract/src/read.ts` (not strict: additive within `/v1`, `API_VERSION`), the projection `packages/server/src/read/` (`index.ts` the `Reader`, `describe.ts` plain words per event kind with no ids in prose, `insights.ts` transcript counts behind the digest's `resolveTranscript` guard, `stream.ts`). It adds no truth and calls no model: a short Issue title is the digest cache's heading (`scopeOf` feeds filed titles of open Issues in ordinary repos only). `/v1/stream` is SSE over the append-only `issue_events` and `events` tables, polled by id each second; the cursor is `i<issue event id>.s<session event id>` (`?since=` or `Last-Event-ID`; malformed or ahead of the tables is 410; no cursor starts at now).

**Behaviour as built** is in `docs/design.md` §3 "As built": the tick, spaces, the runner, hooks and the socket, prompt delivery,
the rules that act, the spool, derived state, sessions, the witness, panes as clients, test slots, quota, admission, the queue
state, roles, process/health/contract/schema/API.

## Layout

- `packages/server` — the lifecycle server: HTTP (`http.ts`), the tick (`tick.ts`), the `Runner` port and its herdr-core
  adapter (`runner.ts`: the port; `hc-runner.ts`, `hc.ts`, `app-doc.ts`; the fixed spaces: `spaces.ts`), derived session state (`sessions.ts`), the hooks' spool (`spool.ts`), the witness
  (`witness.ts`, `hc-events.ts`), the queue (`spawns.ts`, `queue.ts`), admission and capacity (`admission.ts`, `capacity.ts`), the account
  picker's readings (`quota.ts`), prompt delivery (`prompts.ts`), the rules that act (`rules.ts`), the status screen
  (`status.ts`), the test slots (`slots.ts`), Issues (`issues/`: `lifecycle.ts` the one writer, `inbox.ts`, `worker.ts`, `effects.ts`,
  `read.ts`; classify, the lead, its brief, worktree, verbs and send-back: `classify.ts`, `admission.ts`, `lead.ts`, `leadtree.ts`, `names.ts`, `brief.ts`, `worktree.ts`, `verbs.ts`, `sendback.ts`; evidence, the hold and finalize: `evidence.ts`, `commits.ts`, `origin.ts`, `hold.ts`, `finalize.ts`, `archive.ts`, `resume.ts`, `offtick.ts`; what `factory status` and `issue show` read: `follow.ts` (the ISSUES section, the timeline), `attention.ts` (its ATTENTION lines); the ask judge: `judge.ts`, `judge-input.ts`, `agw-call.ts` (the shared `agw` run)), projects (`projects/`: `project.yaml` v0 sync, the make contract, claims; `docs/design.md` §9 "As built"), `migrations/`.
- `packages/contract` — the zod schemas of every response, imported by the server and the CLI, the Issues' (`issues.ts`), the read API's (`read.ts`, over `core.ts`), and the
  role table's schema and loader (`roles.ts`); `spool.ts` is the zod-free half the hook uses (event kinds, the spool line, key and time counting).
- `project.yaml` — this repo's manifest (`docs/design.md` §9); the schema is `packages/contract/src/projects.ts`.
- `config/roles.json` — the role table (FL4).
- `packages/server/src/notify/` — the owner's line (`docs/design.md` §11): the `Notifier` port (`port.ts`: Hermes, null, and the tests' fake), the outbox (`outbox.ts`), the rules and templates (`rules.ts`, `text.ts`), the morning reading (`digest.ts`), `index.ts` the tick's pass. Migration `018`; the away rule is in `outbox.ts`. Config: `FACTORY_NOTIFY_TARGET`, `HERMES_BIN`, `FACTORY_DIGEST_AT`, `FACTORY_DIGEST_TZ`.
- `packages/door` — the factory door: a Bun server, `POST /alert/<source>`, the parsers (`src/parsers.ts`), the tokens file; its README has the HyperDX template.
  Server side: `issues/intake.ts`. LaunchAgent `deploy/com.jkrumm.factory-door.plist.template`, `scripts/launch-door.sh`.
- `packages/cli` — the `factory` binary (`bin/factory.ts`): `version`, `health`, `status`, `spawn list|create|get|cancel|requeue`, `session
  list|get|wait|note`, `slot run`, `queue get|set`, `quota get|refresh`, `role list|get`, `issue new [--after <id> …]|list|show` (`show` is the Issue with its timeline, evidence and questions), `issue phase|wait|ship|close|block|ask|drop <id>` (a lead's report), `issue evidence|reopen|stop|resume <id>`, `issue answer <id> <text>`, `issue note <id> <text>` and `issue prio <id> <n>` (the owner's, token only), `issue facts [--since <iso>]` (one row per attempt from the `factory.issue_facts` view, and the four KPIs), `notify list|test`, `project list|show|sync`, `fleet [--refresh]`, `read overview|issues|issue|sessions|session|asks|health|accounts` and `follow [--issue <id>] [--until-closed]` (the read API, `src/read.ts`), `door route|unrouted|token`, `hook <event>` (`src/hook.ts`). Exit codes are agw's table, copied in `src/exit.ts`.
- `scripts/` + `deploy/` + `.env.tpl` — release-directory deploy as agent-workflows does it (`deploy.sh`, which also does `deploy.sh rollback` for `make rollback`, `launch.sh`,
  `verify.sh`, the LaunchAgent plist template). `launch.sh` also applies `~/.config/factory/env` (`FACTORY_ENV_FILE`; `env-file.sh`): `KEY=VALUE` lines only, mode 0600 and owned by the user, only the non-secret keys `env-file.sh` lists (`FACTORY_PROBE_HOSTS`, `FACTORY_REAPER`, `FACTORY_REVIEW_SESSIONS`, `FACTORY_REVIEW_DEEP_CAP` and `FACTORY_REVIEW_IDLE_MS` are accepted and ignored), else the start is refused; secrets stay in `.env.tpl`; read at launch, so an edit takes a restart.
- `scripts/gameday/` — the F1 kill gamedays: `run.sh <claimed|working>` `kill -9`s the server at a chosen moment and counts what survives; `setup.sh`, `collect.sh`, `teardown.sh` (`factory spawn cancel` for an unclaimed key, else `hc kill` + `hc rm` of the terminal labelled `factory.key=<key>`), `kill-server.sh`, `template/` the scratch repo. Evidence in `docs/evidence/f1-gamedays/`.
- `scripts/gameday/f2/` — the F2 gamedays, live against the deployed factory with real leads: `run.sh <silent-lead|seeded-bug|seeded-bug-regress> [run-id]`, a `report.md` per run in `docs/evidence/f2-gate/`.

## Validate

`make check` — install (frozen), oxfmt check, oxlint (type-aware), shellcheck, `tsc --noEmit`, `bun test`. The tests start a
private Postgres cluster with `initdb` in a temp dir (on PATH, or `PG_BIN_DIR`, or `/usr/lib/postgresql/<major>/bin`
as on GitHub's runners); nothing touches a real database. `make test` runs the tests, `make fmt` formats.
`make deploy`, `make rollback` (back to `data/previous-sha`, health-checked) and `make verify` (the deployed sha is origin/master, or behind it only by docs, markdown or test paths, the `INERT` list of `issues/evidence.ts` mirrored in `scripts/verify.sh`) act on the mini only; `DRY_RUN=1 make deploy|rollback` prints the plan. `FACTORY_REF=<branch>` on
both proves a branch live before it is merged (default `master`). The hc fake for the tests is
`packages/server/test/support/fake-hc.ts` (shapes taken from a scratch core, hc 0.1.15); `HC_E2E=1 bun test packages/server/test/hc-e2e.test.ts` runs the runner and the witness against a scratch core. CI runs `make check` on
`ubuntu-latest`.
