# software-factory

The lifecycle server for agent-built software: it takes in signals and requests, merges duplicates, queues
work against the available Claude Code subscriptions, starts interactive Claude Code sessions in herdr-core terminals that
own a piece of work from root cause to production evidence, follows them through hooks, and closes and
learns. CLI `factory`. Status: live on the mini; `docs/program.md` is the current state.

**Start here:** `docs/decisions.md` (what was decided and why) → `docs/program.md` (tracks, who runs them) →
`docs/design.md` (the design) → `docs/research/` → `docs/evidence/` (the golden set and the
intervention KPIs, moved from dotfiles; `README.md` there says what still re-runs).

## Rules

- **Public repo.** No secrets, hostnames, IPs, tailnet names, internal URLs or account e-mails in any tracked
  file. Placeholders: `<your-domain>`, `<see-1password>`. Secrets resolve at runtime through `secrets-run`.
- **The factory never calls a model.** Every judgment (classify, dedup, wording, learnings) is an `agw`
  workflow; the factory calls `agw` like any other client. No model SDK in this repo.
- **Dependencies point one way:** factory → agw, herdr-core, GitHub, the intake sources. Nothing here is imported
  by agent-workflows.
- **Facts are stored, state is derived.** "Working", "stuck", "waiting" are computed from events when read.
- **Every effect has a deterministic key** (pane names, prompt ids, comment markers), so a replayed tick
  never spawns, prompts or posts twice.
- **Interactive Claude Code in herdr-core only.** Never headless `claude -p`.
- **CLI contract = agw's:** `--format json|plain`, data on stdout, messages on stderr, the same exit codes,
  never prompts.
- Bun, TypeScript strict, zod at boundaries, exact pins (no `^`/`~`; `~/.bunfig.toml` enforces a 3-day release-age
  cooldown, never exclude a package from it). No Effect: the F0 spike decided that
  (`docs/spikes/2026-10-30-effect/verdict.md`).
  The effects are in `docs/design.md` §3 "As built".
- **Never call a port inside a transaction.** The tick claims a row and commits, calls the `Runner` (every call has a
  process timeout), records the result in a new transaction. A failing start is retried until the 30-minute budget, then
  `failed` with a logged reason; `factory spawn requeue <key>` starts it over. Admission is decided again at every claim.
- **Trust boundary.** The token can start Claude Code with `--dangerously-skip-permissions`: a spawn's `repo` and `space` must be
  inside `FACTORY_REPO_ROOTS` after `realpath`, else 422 and nothing stored. The API is loopback only; the tailnet and the
  owner's GitHub user are the perimeter. `FACTORY_REF=<branch>` deploys that branch, the same boundary.
- **The door** (`packages/door`, `docs/design.md` §11): alerts from the tailnet become Issues. It binds loopback only, holds no factory token
  and no database credential, and posts to the socket's `POST /intake`; the repo comes from `factory.door_routes`, never the payload. A down with no route that outlasts 10 min is a health line and one Issue (`issues/unrouted.ts`, `docs/design.md` §11).
- **Hooks: spool first, then post.** `factory hook <event>` does nothing without `FACTORY_SESSION`, appends one line to the
  spool, posts it to the unix socket (300 ms) and exits 0 whatever happens (one exception: the Stop send-back, exit 2).
  `src/hook.ts` imports only `node:fs` and `@software-factory/contract/spool` (no zod, no rest of the CLI) and keeps
  **stdout empty for every event, and stderr too except for a send-back**: Claude Code injects a hook's stdout into the
  session's context. The one exception is a `session-start` with `source: compact` in an Issue lead's session (`lead-<issue>-<attempt>`): one line telling it to re-read the Issue. The socket (mode 0600) is the hook's credential; the witness alone records `runner_restarted` and
  `pane_gone`.
- **Placement and sessions.** The Runner looks before it acts: a terminal carries `factory.key=<spawn key>`, and a live one
  running claude is never started twice. One space per repo, keyed by path; every repo in `FACTORY_SPACES_FILE` (inside `FACTORY_REPO_ROOTS`) has a `plan:<name>` shell tab, a reconcile (`spaces.ts`, every 10 min) that never closes it (`HcRunner.close` refuses a `plan:` key; it is no spawn). A listed root (IuRoot) gets a plan tab too but is never a repo (`resolveSpaceDir` vs `resolveRepo`); an app space with a blank name is named after the entry. Every spawn is a
  tab, any role, with or without a parent.
- **Roles** (`config/roles.json`): role → tier (`haiku|sonnet|opus`, never a model id) and effort. `lead` (sonnet, high) is the level every Issue lead runs at, whatever Classify asked. The table is `lead`, `implementer` (the `spawn create` default), `verifier`, `reviewer` (sonnet, medium: the `/review` subagent) and `Explore`; a spawn with a role not in the table is 422. `rd --role` depends on `factory role get <role> --format json` printing exactly
  `{"role","tier","effort"}`; unknown is exit 4. Values change only on measured data.
- **One process.** A session-level Postgres advisory lock is taken first; a second copy asks for it for 45 s (the old server may be shutting down), then exits 1. Every advisory key lives in
  `src/locks.ts` and they stay distinct.
- **One contract.** Response shapes are zod schemas in `packages/contract`; the server builds every body through its schema and
  the CLI parses with the same one (a body that does not parse is exit 9).
- **One schema, `factory`,** in the shared database; migrations are advisory-locked, qualify every name, and are expand, then
  contract. The `factory` role has no CREATE on the database; `DATABASE_URL` comes from `secrets-run`, never a tracked file.
- **The API is authenticated.** Every route but `GET /health` needs `Authorization: Bearer <FACTORY_TOKEN>`; JSON only (415), at
  most 64 KiB (413), loopback Host (421). The CLI reads `FACTORY_TOKEN` (`factory read|follow` also take `FACTORY_READ_TOKEN`, which the server accepts on `GET /v1/*` only); run it under `secrets-run run --env-file=.env.tpl --`.
- **Tests:** `make test` runs through `factory slot run` when `factory` is installed (a lease; open only when the server is down, a wait past 45 min exits 75 without running; a command past its run limit (30 min default) is killed with exit 124). Update this file in
  the same commit as the code it describes; behaviour goes to `docs/design.md` §3 "As built", not here.
- Direct-to-master, conventional commits, no AI attribution.

**Issues** are `docs/design.md` §4: `src/issues/lifecycle.ts` is the one writer of `issues.state` (a create, always `queued`, is `create.ts`; the door's `intake.ts` files through it); past about 500 lines, stop. `FACTORY_AGW_BIN` is the `agw` Classify calls; `FACTORY_ASK_JUDGE=off` sends every ask to the owner (default on); `FACTORY_ALERT_LEADS=0` keeps `alert` Issues from starting a lead (default on); `FACTORY_LEADS_PER_ACCOUNT` (default 2) caps live Issue leads per account in admission (a lead whose Issue waits on the owner's decision or sleeps in a timed wait is not counted; a lead held by the cap is hold `cap`, with a health line after 15 min); `FACTORY_LOAD_CEILING` (default 60) holds every new Issue lead (hold `load`, health line `held by load`) while the 1-minute load average is above it, running leads are never touched (`admission.ts`); the lead's brief opens with the operating contract (`STANDING_ORDERS`, hash pinned by a test), and the lead opens no terminals; `FACTORY_ARCHIVE_DIR` is where a closed attempt's transcripts go (default `~/.local/share/factory/archive`). `issue_id` goes on a lead's session only. **Every park can end** (RS3, `docs/design.md` §4): the lead's own next turn ends an `unreported` park (as a wall's session ends a `wall`); a `lead_gone` queues the Issue again for the next attempt (finalize first), twice, the third parks; a Stop whose `background_tasks` has an unfinished entry is neither sent back nor parked; the hold first syncs the repo's main checkout to `origin/<default>` (`syncCheckout`, fast-forward only: a checkout on another branch, with a tracked change or diverged is `blocked`, never touched): a blocked hold runs no `make verify`/`make version`, files no `verify_red`, retry or regression, rechecks every 5 min (`CHECKOUT_RECHECK_MS`), shows a health line and gets the steward's `checkout` note; a red verify is retried up to three times (`…:retry1..3`, due 1, 2 and 4 min after the previous red) before it is a `regression`, and the third regression parks the Issue (`parked`). A permission prompt of an Issue lead (`lead-N-M`) is never an owner ask: after 15 min it is one health line naming the command, and nothing is typed. **A decision wait and a timed wait free their repo** (`settleClaims` in `issues/admission.ts`, before admission each tick): an Issue waiting on a `decision` or in a timed `wait` holds no claim; its `answer`, or the end of the wait (the timer, a note with `--wake`, the lead's own `phase`), moves it to `waiting`/`claim`, the pass takes the claim again (`tryClaim`, behind a working holder, ahead of younger queued Issues) and files a `wake` that types the answer (or that the wait is over) and the order to rebase onto the default branch; notes to a lead without a place wait for it. The counts are read from `issue_events`, nothing is stored. `git` and `make verify` never run on the tick or in a transaction: a lead's call waits for its `git`, and `verify` and `finalize` run off the tick (`issues/offtick.ts`). Evidence kind `review`: `ship` also asks agw (`agw review route` for the tier of each of the Issue's own ranges, `agw review covered` over the same ranges: its named and branch commits as first-parent runs of `landedAt`, never what others landed in between, a rebased branch's foreign commits found from its reflog; `commits.ts` `reviewRanges`, `issues/review.ts`, `derive` stores `derived.review`). It is required when the tier is not `none` and met only by agw's coverage (every first-parent commit reviewed at its tier, no open important finding), never by a filed `--kind review --link`. An agw failure refuses the ship (fail closed). `close` is not asked. `factory.issue_facts` (migration `033`) is a view: one row per attempt, the attempt derived from the `admitted` events, no usage read, no review rounds (`docs/design.md` §4 "Issue facts"). **Dependencies and priority:** admission looks only at an Issue with no `issue_deps` row (a close deletes its rows, so a row is an open dependency) and orders a project's candidates by the latest `prio` event (none = 0), then id, so a blocked oldest holds nothing back; `issue new --after <id>` writes the rows in the create's transaction (an unknown or closed id: 422, nothing stored; a repeat of a `--key` ignores `--after`), `issue prio <id> <n>` files the event, and nothing is stored on the Issue.

**Intake** (`docs/design.md` §4 "Intake: work comes in by itself"): `issues/signals.ts` `fileSignalIn` is the one entry for every source (the door's `intakeAlert` calls it with its route's repo; a poller passes its own `repo`): replay by Issue key, inbox key or `factory.intake_seen`, one episode per `(source, subject)` in `door_issues`, a stateless `fingerprint` repeats an open Issue or one filed less than `FINGERPRINT_WINDOW_MS` (24 h) ago, `INTAKE_SOURCES` (`create.ts`) are all refused in IuRoot. A `down` with a matching manifest `heal:` rule stores `intake_pending` (migration `037`) and answers `settling`; `issues/settle.ts` `settlePass` (tick, after `projectPass`) runs `make -C <repo> restart` outside any transaction (lease, `max` tries), then files the Issue or an `up` answers `healed`.

**Intake off the tick:** the tick only kicks the slow parts. `issues/settle.ts` `Settler` (`kick`/`settled`, errors kept for the next tick) runs the settle pass, so a `make restart` never holds a tick. `intake/github.ts` `GithubIntake` polls the projects with `signals.github` in the manifest (label, default `factory`; `owner/name` from `origin`; open issues, never pull requests) every `FACTORY_GITHUB_POLL` (default `5m`, `off`) and files each through `fileSignalIn` as source `github`; it needs `FACTORY_GITHUB_TOKEN` (`.env.tpl`), without it the source is off with one log line; the issue text is data. `intake/beszel.ts` `BeszelIntake` polls the Beszel hub every `FACTORY_BESZEL_POLL` (default `1m`, `off`; `FACTORY_BESZEL_URL` in the env file, `FACTORY_BESZEL_EMAIL` and `FACTORY_BESZEL_PASSWORD` in `.env.tpl`; any missing = off with one log line) and files source `beszel` signals (`<system>:<rule>`, `down`/`up`) through `fileSignalIn` for the hosts of `config/infra.json` (routing and every threshold, loaded at startup by `intake/infra.ts`, a bad file is a startup error); `intake/beszel-rules.ts` is the pure rule evaluation, no model; `beszel` is in `INTAKE_SOURCES`; semantics in `docs/design.md` §4 "Beszel". **Stop the line** (`admitIssues`): while a project has an episode Issue (`facts.status = down`, so never a GitHub label) `queued` or `working`, only such a fix, or an urgent Issue, is admitted there, and the fix goes first.

**The plan** (`docs/design.md` §4 "The plan files its next Issue"): `docs/plan.yaml` per repo, read by the project sync off the default branch (`projects/plan-file.ts`, `plan-status.ts` the derived row states and the health lines, `plan.ts` the filing in `projectPass`, schema `packages/contract/src/plan.ts`, migration `036`); a row is filed as an Issue of source `plan` (key `<project>:<row>`) when its `after` rows are closed in any outcome and `not_before` / `stable_days` hold. This repo's own plan is `docs/plan.yaml`.

**The steward** (`src/issues/steward.ts`, `docs/design.md` §4 "The steward"): once per tick, after the timers and before the inbox, it files inbox events for a stalled Issue and never moves state itself (a model is never called; the one new edge is `restart`, a `lead_gone` park to `queued`): a wake `note` for a `blocked`, `parked` or `unreported` Issue whose lead is live (a block naming the verification re-runs it off the tick first), a nudge `note` for a silent or over-budget lead (a lead whose last event is a stop with background work in flight, `leadsOnBackgroundWork`, is not silent), a `restart` for a `lead_gone` park, a `checkout` note for a `watching` Issue whose hold is blocked on its checkout, the holder's wake when an Issue has queued 15+ min behind its claim (never for a timed `wait`, which holds no claim). Backoff 30 min, 2 h, 6 h from when the cause began, at most 3 acts per Issue and cause (keys `steward:<issue>:<cause>:<n>`, counted from the inbox, nothing stored); then one `steward_exhausted` event; the ask judge (below) then answers it with a `note` or records the one outbox line `notify:steward:<issue>:<cause>`. `factory status` shows `steward { acts, exhausted }`. A `note` prompt for a `lead-…` session pending 5 min while the lead is `working` is typed anyway (`Runner.type` `force`), proven by a `turn_ended` too. A `needs a human` review line is gone once the job was taken, its repo has no open Issue, or it is a day old.

**The ask judge** (`src/issues/judge.ts`, `judge-input.ts`, `agw-call.ts`; `docs/design.md` §4 "The ask judge"): each new decision and each `steward_exhausted` event is judged by `agw factory-ask` off the tick before the owner hears of it (`recordDecision` and `exhaust()` no longer notify; the pass sends `notify:ask:<id>` / `notify:steward:…` once). Verdict `answer` passes the guards (one of the options, a source, a declared default only if `isDoNothing`) and is filed as an inbox `answer` from `steward` (`judge:<id>`), reversible by an owner note. Owner, any failure, `FACTORY_ASK_JUDGE=off` (default on) or no judge: the ask stands as before. A visible (IuRoot) repo sends nothing to `agw`. A new ask is hidden from `attention` until `ask_judged:<id>` exists, for at most 45 min.

**Asks and health** (RS3, `docs/design.md` §3 `factory status`, §11 "The fleet view"): an ask is a decision only (`decision`, an Issue `blocked`, hc's `blocked` prompt, a `wait` on the owner, the human queue). Everything else that needs a look is a health line, never an ask: every park with reason and age, `stuck`, `walled`, failed spawns and notes, undelivered notifications, a lead that did not start, a silent lead (no event for 20 min), a started spawn with no first turn 3 min after its start (its brief may sit unsent; `briefs.ts` presses Enter for it), an Issue over its size's budget (s 2 h, m 6 h, l 24 h), two regressions. `factory status` has `attention` (asks) and `health`; `/fleet` has `asks` and `health[]` (`src/health.ts`: the derived lines, `healthKind`, and the `heartbeat` on `GET /health`, `{ok, reason, tickAt, queueMovedAt}`, whose names a pusher reads: do not rename them). A line is in one list. **A line about something finished ends 72 h after it finished** (`FINISHED_HEALTH_MS` in `src/health.ts`: a failed spawn, a failed note, an undelivered notification, a kept worktree); an ongoing one stays while true. Derived at read, nothing stored.

**The fleet view** is `docs/design.md` §11 "The fleet view": `src/fleet/` (`index.ts` the builder the tick kicks, `model.ts` the pure assembly, `sources.ts` hc and the human queue read-only, `place.ts` which places are IuRoot's, `store.ts` the one-row snapshot `factory.fleet_snapshot` and `NOTIFY fleet`, `digest-model.ts` where the digest meets the model), `GET /fleet` and `POST /fleet/refresh` (**token API only**: the model holds IuRoot's text, so the socket answers 404), `factory fleet` (needs `FACTORY_TOKEN`, exit 3 without). The model is slim and read-only: repos with their live sessions, `issues[]` (the open Issues), `asks[]` (hc blocked, a wait on the owner, factory, decision, the human queue, the digest's `reply`), `health[]`, `summary`, `queue`, `quota`, `errors`, `digest`. It has no plans, git state, tiers, actions, presence or reaper. The model itself reads and calls no model; **the digest** (`src/fleet/digest*.ts`, `transcript.ts`; `docs/design.md` §11 "The digest") asks `agw digest` about what changed every `FACTORY_DIGEST_EVERY` (default `5m`, `off`) and the snapshot reads its cache (`headline`, `short`, `source: reply` asks); a fourth item kind, `line`, words an ask or health line for the read API only (asked as agw kind `session`, cache `line:<hash>`); a fifth, `about`, words an open Issue's filed title and goal into one sentence on what it is for (agw kind `session`, cache `about:<issue>`, ordinary repos only); **nothing of a `visible` (IuRoot) repo or session is ever sent, and no line text that mentions IuRoot or a visible repo's name** (`scopeOf` is the one place that decides). Config: `FACTORY_VISIBLE_ROOTS` (read-only roots, default `~/IuRoot`, `off`), `FACTORY_ASK_HUMAN`, `FACTORY_DIGEST_EVERY`. The owner is always treated as away: only a decision, the steward's spent retries, a finished plan (`notify:plan:`), the morning reading and a test go out (`notify/outbox.ts` `foldReason`); the 07:30 message is built from facts (Issues shipped in 24 h, the snapshot's asks, health and open Issues, no model text; `notify/digest.ts`).


**The read API** is `docs/design.md` §11 "The read API": `GET /v1/overview|issues|issues/:id|sessions|sessions/:id|asks|health|accounts|stream`, **token API only** (the socket answers 404 for all of `/v1`; it holds IuRoot's text and marks it `visible`). **The read token** (`FACTORY_READ_TOKEN`, optional, at least 16 characters, different from `FACTORY_TOKEN`) is a second bearer for surfaces (the Hermes agent, whose input goes to models): it passes on `GET /v1/*` only (403 `this token reads /v1 only` anywhere else, POST on a `/v1` path included; unset, it is 401) and `read/surface.ts` leaves out the text of everything `visible` under it (an Issue's title, goal, notes, timeline, evidence and questions; a session's title and transcript path; an ask or health line, whose id becomes `redacted:<hash>`; a visible spawn's place; a visible Issue's stream text is its event kind). Visibility is `scopeOf`'s rule (`namesVisible` included: a line naming IuRoot or a visible repo is `visible`). `FACTORY_TOKEN` reads unredacted as before. The CLI's `read` and `follow` fall back to `FACTORY_READ_TOKEN`; every other verb needs `FACTORY_TOKEN`. Schemas `packages/contract/src/read.ts` (not strict: additive within `/v1`, `API_VERSION`), the projection `packages/server/src/read/` (`index.ts` the `Reader`, `describe.ts` plain words per event kind with no ids in prose, `plain.ts` ids out of an ask or health line and the deterministic `short`/`summary` fallback, `insights.ts` transcript counts behind the digest's `resolveTranscript` guard, `stream.ts`). It adds no truth and calls no model: a short Issue title is the digest cache's heading (`scopeOf` feeds filed titles of open Issues in ordinary repos only). `/v1/overview` `asks` are the factory's own asks (`counts.asks` = `factory status` attention), the dotfiles human queue is `humanQueue` (`stale` past 24 h, only not stale ones in `counts.humanQueue`); every ask and health line has plain `short`/`summary` (digest `line` answer, else fallback) and a one-line `text`; a lead's `reply` ask is dropped when its Issue has a `decision` ask. `/v1/stream` is SSE over the append-only `issue_events` and `events` tables, polled by id each second; the cursor is `i<issue event id>.s<session event id>` (`?since=` or `Last-Event-ID`; malformed or ahead of the tables is 410; no cursor starts at now).

**Behaviour as built** is in `docs/design.md` §3 "As built": the tick, spaces, the runner, hooks and the socket, prompt delivery,
the rules that act, the spool, derived state, sessions, the witness, panes as clients, test slots, quota, admission, the queue
state, roles, process/health/contract/schema/API.

## Validate

`make check` — install (frozen), oxfmt check, oxlint (type-aware), shellcheck, `tsc --noEmit`, `bun test`. The tests start a
private Postgres cluster with `initdb` in a temp dir (on PATH, or `PG_BIN_DIR`, or `/usr/lib/postgresql/<major>/bin`
as on GitHub's runners); nothing touches a real database. `make test` runs the tests, `make fmt` formats.
`make deploy`, `make rollback` (back to `data/previous-sha`, health-checked) and `make verify` (the deployed sha is origin/master, or behind it only by docs, markdown or test paths, the `INERT` list of `issues/evidence.ts` mirrored in `scripts/verify.sh`) act on the mini only; `DRY_RUN=1 make deploy|rollback` prints the plan. `FACTORY_REF=<branch>` on
both proves a branch live before it is merged (default `master`). The hc fake for the tests is
`packages/server/test/support/fake-hc.ts` (shapes taken from a scratch core, hc 0.1.15); `HC_E2E=1 bun test packages/server/test/hc-e2e.test.ts` runs the runner and the witness against a scratch core. CI runs `make check` on
`ubuntu-latest`.
